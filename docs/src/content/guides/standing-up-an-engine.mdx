This guide builds [our engine](../our-engine/) from an empty AWS account. Run each step from a komrad checkout. The mise tasks use the AWS profile named komrad unless your environment already has credentials.

## Prerequisites

- An AWS account with a named profile, and an S3 bucket for Terraform's state.
- The Session Manager plugin for the AWS CLI. The machine has no SSH, so this is how you get a shell.
- A domain for the engine at a DNS host you control, such as `komrad.example.com`.
- Komrad registered with your identity provider as a desktop app. [Access](../engine-access/#registering-komrad-with-the-provider) covers the registration.
- A GitHub App for the engine, with its private key stored in Secrets Manager as `komrad/github-app`. [Forge credentials](../forge-credentials/#github) covers the App. Store the key before the first boot, so the machine finds it.

## Building the image

```sh
mise run packer:build
```

The build prints the image's id when it finishes. [The machine](../engine-machine/) describes what the image contains.

## Applying the infrastructure

Copy `terraform.tfvars.example` and `backend.hcl.example` in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine), remove the `.example`, and fill them in. The variables include your account, region, the image id and the engine's `domain_name`. The `github_*` values and `state_bucket` let GitHub Actions deploy. Then run:

```sh
mise run infra:engine:init
mise run infra:engine:apply
```

The apply prints the instance's address as `instance_public_ip`, its id as `instance_id`, and the CI role as `ci_role_arn`.

Add an A record for the domain at your DNS host, pointing at `instance_public_ip`. Terraform doesn't manage the record, so the engine works with any DNS host. Caddy requests its certificate once the record resolves.

On first boot, the machine mounts its data volume, migrates the database, creates the engine's login, and starts the server and Caddy. Open a session and check that no unit failed:

```sh
aws ssm start-session --target i-0123456789abcdef0
systemctl list-units --state=failed --no-legend
```

## Configuring GitHub Actions

Set these variables on the repository so the release and schedule workflows can reach the engine:

- `AWS_CI_ROLE`, from the `ci_role_arn` output
- `AWS_REGION`
- `TF_STATE_BUCKET`
- `TF_STATE_KEY`, matching the key in your backend file

If you changed the stack's `name`, set `ENGINE_NAME` to match. Workflows skip their engine steps until `AWS_CI_ROLE` is set.

## Configuring the engine

In a session on the machine, switch to the komrad account:

```sh
sudo -u komrad -i
```

Edit `~/.config/komrad/config.toml`:

- Name your identity provider and komrad's client id. For Google, add the client secret too.
- Add the <Setting path="github_app" label="[github_app]" /> table with the App's id, its installation id, and `/run/komrad/github.pem` as the key's path.
- Turn on <Setting path="harness.claude.trust_launch_dirs" label="trust_launch_dirs" /> for each agent CLI, so new agents don't stop to ask whether to trust their worktree.

Check that <Command path="github token" /> prints a token, then restart the server to load the config, as [runbooks](../runbooks/#restarting) shows.

As the komrad account, start each agent CLI once and sign it in, then clone the repositories agents will work in. The logins and clones live on the data volume and survive a rebuild.

## Granting your own access

Exit the komrad account's shell and grant yourself access:

```sh
sudo komrad-access grant you@example.com
```

On your laptop, create `~/.config/komrad/engines/remote.toml`:

```toml
[connection]
url = "https://komrad.example.com"
```

Sign in and open the panel:

```sh
komrad login --engine remote
komrad open --engine remote
```

## Connecting the forge

From your laptop, run <Command path="forge connect" args="github.com --method github-app --engine remote" />. The server mints its tokens from the App's key, so there is no token to paste. To connect GitLab as well, see [forge credentials](../forge-credentials/#gitlab).

[Runbooks](../runbooks/) covers running the engine from here, through [tearing it down](../runbooks/#tearing-it-down).
