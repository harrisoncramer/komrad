Komrad is one binary. The same binary runs the panel and the server.

The panel runs on your machine. It renders the view of komrad's state in your terminal, and wraps around existing CLI tools like Claude or Codex.

The server runs your agents and records their activity in Postgres, so you can search chat history, spawn several agents at once, or have them communicate. The server, along with its database and agents, makes up an _engine_. Komrad's engines can run on your machine or on a remote box and one panel can connect to different engines.

## Quick start

Komrad runs its agents in tmux, so install tmux 3.3 or newer first. Then run the install script.

```sh
curl -fsSL https://github.com/harrisoncramer/komrad/releases/latest/download/install.sh | sh
```

The script downloads the newest stable release for your platform into `~/.local/bin`, checks it against the release's checksums, and runs <Command path="setup" />. Setup asks for whatever the machine is missing, such as where to keep the database, then prints a report from <Command path="doctor" />. If setup stops part way, fix what it names and run <Command path="setup" /> again.

Run <Command path="open" /> to open the panel.

To install the `tip` release, set `KOMRAD_VERSION=tip` on the `sh` side of the pipe. `KOMRAD_VERSION` also takes a release tag such as `v0.3.0`. `KOMRAD_INSTALL_DIR` picks a directory other than `~/.local/bin`.

```sh
curl -fsSL https://github.com/harrisoncramer/komrad/releases/latest/download/install.sh | KOMRAD_VERSION=tip sh
```

## Manual installation

The install script downloads the binary, checks it and runs setup. To do each step yourself, follow this section.

<Alert title="Having trouble?" variant="warning">
  Run <Command path="doctor" /> to check for configuration or installation issues.
</Alert>

### Install the binary

```sh
mkdir -p ~/.local/bin
curl -fsSL -o ~/.local/bin/komrad https://github.com/harrisoncramer/komrad/releases/latest/download/komrad-darwin-arm64
chmod +x ~/.local/bin/komrad
```

Swap `darwin-arm64` for your platform: `darwin-amd64`, `linux-amd64` or `linux-arm64`.

This installs the newest stable release. Each release has a version number and a changelog on the [releases page](https://github.com/harrisoncramer/komrad/releases).

### Check the download

Every release carries a `checksums.txt` file. Compare the binary against it.

```sh
expected="$(curl -fsSL https://github.com/harrisoncramer/komrad/releases/latest/download/checksums.txt |
  awk '$2 == "komrad-darwin-arm64" {print $1}')"
echo "$expected  $HOME/.local/bin/komrad" | shasum -a 256 --check
```

The checksums come from the same place as the binary, so they catch a corrupted download, not a compromised release.

### Install tip instead

The `tip` release is rebuilt from main on every merge. It has the newest changes and makes no version promise.

```sh
mkdir -p ~/.local/bin
curl -fsSL -o ~/.local/bin/komrad https://github.com/harrisoncramer/komrad/releases/download/tip/komrad-darwin-arm64
chmod +x ~/.local/bin/komrad
```

### Run setup

Run <Command path="setup" /> once the binary is on your PATH. It walks through the machine one step at a time. To set the machine up by hand instead, follow the rest of this section.

### Create your database

Every release binary carries an embedded Postgres, so you do not need to install or run it yourself. Run <Command path="setup" /> or pass `--embedded-postgres`, and komrad creates the database, an engine named `default`, and your <Setting path="connection" label="[connection]" /> block.

```sh
komrad setup --no-input --embedded-postgres
```

After a restart, <Command path="start" /> or <Command path="open" /> brings the embedded Postgres back up.

### Use a Postgres you already run

You can keep the database yourself instead, for example in Docker.

```sh
docker run --name komrad \
	-e POSTGRES_USER=komrad_owner \
	-e POSTGRES_PASSWORD=password123 \
	-e POSTGRES_DB=komrad \
	-p 5432:5432 \
	-v komrad_data:/var/lib/postgresql \
	-d postgres:18
```

Postgres takes a few seconds to start. Wait until `docker exec komrad pg_isready -h localhost` reports that it is accepting connections before moving on.

The database needs one admin-like user. The komrad engine uses this user to run migrations each time you update your binary. Choose "A Postgres I already run" in <Command path="setup" /> and paste this user's URL, or pass it as `--owner-database-url`. To do the same by hand, provide the URL to the <Command path="migrate" /> command and create your first engine. The engine is named `default` here.

```sh
export KOMRAD_OWNER_DATABASE_URL=postgres://komrad_owner:password123@localhost:5432/komrad
komrad migrate
komrad engine ensure default
```

Several engines can share one database, so multiple developers can share a Postgres database, or one developer can spread their workload across machines.

### Write the config

Komrad's configuration is stored in a TOML file. Setup writes this file for you when there is none. This section is for a Postgres you set up by hand, or a config file you already have.

The <Command path="engine ensure" /> command prints an initial <Setting path="connection" label="[connection]" /> block with a login for the engine. Run it, put the engine block in `~/.config/komrad/config.toml`, and add the owner URL from the previous step beside it.

```toml
[connection]
owner_database_url = "postgres://komrad_owner:password123@localhost:5432/komrad"
database_url = "postgres://komrad_engine_default:8f3a1c9e2b7d4e6f@localhost:5432/komrad"
```

Only <Command path="migrate" />, <Command path="engine ensure" />, <Command path="engine grant" /> and <Command path="engine revoke" /> use the <Setting path="connection.owner_database_url" label="owner_database_url" />. The server itself connects with <Setting path="connection.database_url" label="database_url" />.

### Open the panel

Komrad runs every agent in a tmux server of its own, so tmux must be installed. Using tmux yourself is optional.

Run <Command path="open" /> to open the panel. The first open starts the server in the background, and the embedded Postgres too if you use it.

## Connecting a forge

Komrad can push or pull data from your forge, such as GitHub or GitLab, only after you connect it. Connect a forge once with the <Command path="forge connect" /> command.

### GitHub

On your laptop, the simplest way is to hand komrad the token the GitHub CLI already holds.

```sh
gh auth token | komrad forge connect github.com
```

Any personal access token works the same way, as long as it can read the pull requests of your repositories. For GitHub Enterprise, add `--kind github` and, if needed, `--api-url`.

To connect a GitHub App, set it up in <Setting path="github_app" label="[github_app]" /> and connect it with `--method github-app`. Komrad makes a token from the App, which expires after an hour, and makes a new one whenever it needs to. [Komrad's engine](../komrads-engine/#github) covers registering the App.

```sh
komrad forge connect github.com --method github-app --engine remote
```

### GitLab

GitLab takes a personal access token with the `api` scope.

```sh
komrad forge connect gitlab.com --token-file ~/.config/gitlab-token
komrad forge connect gitlab.example.com --kind gitlab --token-file ~/.config/gitlab-token
```

GitLab has no App to make short-lived tokens from. On a machine other people can reach, such as a remote engine, connect with `--method rotating-token` so the token komrad holds does not live forever. Komrad swaps the token for a new one as soon as you connect, so the one you pasted stops working at once.

Use <Command path="forge disconnect" /> to revoke the current token with GitLab before you forget it.

```sh
komrad forge connect gitlab.com --method rotating-token --token-file ~/.config/gitlab-token --engine remote
```

If a rotation is ever refused, the connection shows as refused in <Command path="forge list" />. Connect it again with a fresh token.

### Self-Hosting

A self-hosted forge needs two more things.

Komrad cannot tell from a host's name which forge it runs, so pass `--kind github` or `--kind gitlab`. If its API is somewhere other than `https://<host>/api/v3` for GitHub or `https://<host>/api/v4` for GitLab, pass `--api-url` as well.

Some hosts take SSH paths like `ssh.gitlab.example.com`. List each pair in <Setting path="git.ssh_hosts" label="ssh_hosts" /> so a remote on the SSH name finds the connection for the web host. Public names such as `ssh.github.com` and `altssh.gitlab.com` are already known.

## Upgrading

Run the install script again or download the new binary over the old one, then stop the server and migrate. The install script skips setup when it replaces a binary.

```sh
komrad stop
komrad migrate
```

A running server keeps its old build until you stop it. Open the panel again and it starts the new build. The embedded Postgres keeps running through <Command path="stop" />, so <Command path="migrate" /> can still reach it. Agents keep running throughout, because they live in tmux, not in the server.

## Running the panel inside tmux

The panel is a terminal application, so it runs inside tmux without a problem.

If your own tmux prefix is `ctrl+space`, give your tmux a different one, because the panel keeps its own keys behind it.
