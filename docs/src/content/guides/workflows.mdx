Everything you do in komrad happens inside a _workflow_. A workflow is a bucket of settings. It holds the directory work starts from, the harness its agents run, like Claude or Codex, the flags they launch with, and whether each task gets a worktree of its own.

<Alert variant="warning">This guide assumes you have [installed komrad](../install/) already.</Alert>

Think of a workflow as a shared blueprint for one kind of work in one repository. You might keep one for bug fixes and another for feature work in the same repository, each with its own flags and context.

## Creating your first workflow

Clone a real repository to work in. This guide uses Neovim.

```sh
git clone https://github.com/neovim/neovim ~/neovim
cd ~/neovim
```

Run <Command path="open" />, open the menu with <Key name="menu.open" /> and press <Key name="menu.new_workflow" />. Name the workflow `neovim`. Its directory defaults to the one you opened komrad in, and its provisioner decides whether each task gets a worktree. Press enter to create it.

The orchestrator writes no code of its own. You tell it what you want done, and it creates [tasks](../tasks/) for the work and puts agents on them. It passes messages between those agents and gathers what they find. Think of it as a lead who splits the work up and keeps track of it.

## Workflow owners

On a [remote engine](../remote/), each workflow has a workflow owner: you, or the bot, the engine's own account on GitHub. You pick it when you create the workflow, and it never changes. A workflow on your laptop always belongs to you.

Your own workflow runs on your dev box. Its tasks, its orchestrator and its schedules all act as you, with your GitHub access. Nobody else sees it.

A bot workflow runs each task on a worker of its own, and its orchestrator on one more. Its agents act as the bot. Everyone with access to the engine sees the workflow and can start its tasks.

A bot workflow also names its repository set, the repositories its tasks may touch, which is its own origin unless you add more. Each task keeps the set it started with, and GitHub refuses its agents anything outside it.

## Shared context

A workflow can carry _shared context_, which every agent it starts reads. Use it for anything you would otherwise tell each agent by hand, such as how tests run and how commits are written.

In the Neovim example, that might be "Run make lint before committing any Lua change."

The workflow's context comes after your <Setting path="context">global context</Setting>, which every agent reads in any workflow. In the video below the global context says only that Neovim is the best editor, and the agent has read both.

## Worktrees

Komrad has first-class support for [git worktrees](https://git-scm.com/docs/git-worktree). Set the workflow's provisioner to worktree and each new task gets a worktree of its own, cut from the workflow's base branch. Every agent on that task works inside it, isolated from every other task. Komrad locks each worktree, so a `git worktree prune` in your own checkout keeps its registration. Deleting the task unlocks and removes the worktree.

Komrad puts worktrees in <Setting path="worktrees.dir" /> unless the workflow names a directory of its own. The worktree section of the workflow's settings also lists files to copy or link into each new worktree, such as a `.env` file git does not track.

A workflow can also name a setup command. Komrad runs it in the worktree before an agent starts or resumes there. Point it at whatever prepares the repository, such as `mise trust && mise install`, `npm ci` or a script the repository keeps. mise refuses the config in a directory it has not trusted, and each worktree is a new directory, so the example trusts it first. When the command fails, the agent does not start.

When you start a task, you _can_ run it in the workflow's base directory instead of a worktree.

<Alert variant="danger">
  Tasks without a worktree should usually not be asked to write code; they'll alter shared files.
</Alert>

This is helpful if you want to spawn an agent to make a change to your local directory, or if you do not want the agent to write any changes at all.

## Changing a workflow

Hover the workflow, open the menu with <Key name="menu.open" /> and pick edit with <Key name="menu.edit_row" />. The settings are the same as when you created it, plus the [hooks](../hooks/) and the prompts komrad sends agents when something happens.

## Archiving and restoring

Archiving a workflow puts it in cold storage. Open its menu with <Key name="menu.open" /> and press <Key name="menu.archive" />. Komrad archives the workflow's orchestrator, its tasks, and every live agent in it. On a remote engine, a bot workflow's workers go away and their volumes stay. Nothing is deleted. The workflow moves to the archive, where you can restore it or delete it for good later.
