Agents perform work in komrad. Each one is a real Claude or Codex session running in a terminal that komrad manages for you. Agents are designed to be stateless in komrad, so that you can easily create or discard them without losing work.

<Alert variant="warning">
  This guide assumes you know what a [workflow](../workflows/) and a [task](../tasks/) are.
</Alert>

They are also durable. You can shut down or restart your machine without losing any history or context with an agent, and easily restore or search through their conversations later. Agents can also start and manage other agents.

## Three kinds of agent

Komrad has three kinds of agents.

There is always one _orchestrator_ agent per [workflow](../workflows/#the-orchestrator). It sits above the workflow's tasks rather than inside any of them, and coordinates the work across them.

Every task has exactly one _writer_. The writer does the task's work: it makes edits, commits, and opens the pull request. It is the only agent that changes the task's checkout, and it stays with the task for the task's whole life. You can [restart](../tasks/#restarting-the-writer) it on a new conversation whenever you want.

Finally, _reviewer_ agents read the writer's change and comment on it. A reviewer belongs to the task, not to the writer. It works in the task's checkout but makes no changes of its own.

```
  workflow: neovim
   |-- orchestrator         <-- coordinates the workflow's tasks
   |
   |-- task: fix-login
   |      |-- writer        <-- does the work, owns the checkout
   |      '-- reviewer      <-- reads the writer's change
   |
   '-- task: rfc-truncate
          '-- writer
```

The list draws the same tree. A task and its writer share one row under the workflow, and the task's reviewers sit beneath it.

## Starting agents

Most of the time you start an agent by [starting a task](../tasks/#starting-a-task), which launches its writer. The other way is to ask the orchestrator. Tell it what you want done and it creates the tasks, puts a writer on each, and writes each one a brief.

## Reviewers

Usually the writer asks for a review when it thinks its work is ready, and komrad starts a reviewer on the task. The reviewer reads the change and leaves comments on its lines, the same way you do in a [review](../reviews/), and the writer answers them. While a reviewer is still reading, the writer cannot ask for another. Over a task's life it can go through many.

You can start a reviewer yourself too. Open a task's menu and pick new agent with <Key name="menu.new_agent" />, then say what you want looked at. The orchestrator can do the same. Either way it is still a reviewer, so it reads the change and talks to the writer, but never edits the checkout.

Set <Setting path="usage.task.max_reviewers" /> to cap how many reviewers one task can hold at a time.

## Adopting work

Sometimes the work started outside komrad, such as a colleague's pull request or a branch you began on another machine. Hover the workflow, open the menu with <Key name="menu.open" /> and press <Key name="menu.adopt" />. Name the branch and say what to do with it. Komrad starts a task on that branch with a writer on it, in a worktree of its own when the workflow cuts them.

The branch has to be in the workflow's repository, either pushed to its origin or already on disk.

## Archiving and deleting an agent

Archiving an agent stops it and takes it out of the list. Its conversation stays in the database, so you can still search it or restore it later.

A writer and its task share one life, so you never archive a writer on its own. Archive the [task](../tasks/#archiving-restoring-and-deleting-tasks) instead, which archives the writer and every reviewer on it. Restoring the task brings its writer back.

Reviewers come and go on their own. You can archive one whenever you like, and restore it later once its task is live. Deleting an archived reviewer is permanent and removes its conversation. A writer is deleted only with its task.

## How komrad knows what an agent is doing

Most agent tools learn what an agent is doing from hooks the agent fires. Hooks can be dropped, reordered, or never sent, for example when the CLI crashes. When that happens, those tools show an agent as working when it is idle, or waiting when it is done.

Komrad reads each agent's state from what its terminal actually shows, which komrad calls the pane. The [Claude test panes](https://github.com/harrisoncramer/komrad/tree/main/internal/harness/claude/testdata) show what it reads.

This has a cost. If a process dies, komrad still sees it, but a new release of Claude or Codex that draws its screen differently can confuse it. If Claude or Codex ever ship real-time state notifications, komrad will move to them. Until then, reading the pane is the more reliable choice.

If the state shown does not match your CLI, please <a href={link('/guides/bug-reports')}>submit an issue</a> on GitHub.
