This guide builds [komrad's engine](../komrads-engine/) from an empty AWS account, with each step in the order the later ones depend on. Run every command from a komrad checkout. The mise tasks use the AWS profile named komrad unless your environment already has credentials.

## Prerequisites

- An AWS account with a named profile, and an S3 bucket for Terraform's state.
- The Session Manager plugin for the AWS CLI, which you need to get a shell on the machine.
- A Tailscale tailnet with MagicDNS and HTTPS certificates turned on in its DNS settings, and Tailscale running on your laptop.
- The engine's rules in the tailnet's access policy, as [Access](../engine-access/#the-tailnet-policy) shows. Add them before the engine joins.
- An auth key for the engine from Tailscale's admin console. Make it single-use and pre-approved, and tag it `tag:komrad-engine`. Store it in Secrets Manager as `komrad/tailscale-auth-key`. The engine uses it only on first join.
- Komrad registered with your identity provider as a desktop app. [Access](../engine-access/#registering-komrad-with-the-provider) covers the registration.
- A GitHub App for the engine, with its private key stored in Secrets Manager as `komrad/github-app`. [Forge credentials](../forge-credentials/#github) covers the App. The machine reads the key at boot, so store it before the first one.

## Building the image

```sh
mise run packer:build
```

The build prints the image's id when it finishes, and Terraform needs that id in the next step. [The machine](../engine-machine/) describes what the image contains.

## Applying the infrastructure

Copy `terraform.tfvars.example` and `backend.hcl.example` in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine), remove the `.example`, and fill them in. The variables include your account, the region, the image id, and the `sign_in_*` values from your provider. Set `tailscale_hostname` to the engine's name on the tailnet, which defaults to komrad, and `tailscale_tailnet` to your tailnet's DNS name, such as `tail1234.ts.net`. GitHub Actions needs the `github_*` values and `state_bucket` to deploy. Then run:

```sh
mise run infra:engine:init
mise run infra:engine:apply
```

The apply prints the engine's address as `engine_url`, its instance id as `instance_id`, and the CI role as `ci_role_arn`.

On first boot, the machine joins the tailnet, mounts its data volume, migrates the database, creates the engine's login, and starts the server and Caddy. Once the engine shows up in Tailscale's admin console, revoke the auth key there and delete the secret without a recovery window, so the name is free when you need a new key:

```sh
aws secretsmanager delete-secret --secret-id komrad/tailscale-auth-key --force-delete-without-recovery
```

Open a session and check that no unit failed. On a healthy machine the second command prints nothing:

```sh
aws ssm start-session --target i-0123456789abcdef0
systemctl list-units --state=failed --no-legend
```

## Configuring GitHub Actions

The release and image workflows reach the engine through these repository variables:

- `AWS_CI_ROLE`, from the `ci_role_arn` output
- `AWS_REGION`
- `TF_STATE_BUCKET`
- `TF_STATE_KEY`, matching the key in your backend file

If you changed the stack's `name`, set `ENGINE_NAME` to match. The workflows skip their engine steps until `AWS_CI_ROLE` is set.

## Configuring the engine

In a session on the machine, switch to the komrad account, which owns komrad's config:

```sh
sudo -u komrad -i
```

Edit `~/.config/komrad/config.toml`:

- Add the <Setting path="github_app" label="[github_app]" /> table with the App's id, its installation id, and `/run/komrad/github.pem` as the key's path.
- Turn on <Setting path="harness.claude.trust_launch_dirs" label="trust_launch_dirs" /> for each agent CLI, so new agents don't stop to ask whether to trust their worktree.

Check that <Command path="github token" /> prints a token. Then restart the server so it loads the new config, as [runbooks](../runbooks/#restarting) shows.

Still as the komrad account, start each agent CLI once and sign it in, and clone the repositories the agents will work in. The logins and the clones live on the data volume, so they survive when the instance is replaced.

## Granting your own access

Exit the komrad account's shell and grant yourself access:

```sh
sudo komrad-access grant you@example.com
```

Add yourself to the group your tailnet policy lets in. Then, on your laptop, create `~/.config/komrad/engines/remote.toml` with the `engine_url` the apply printed:

```toml
[connection]
url = "https://komrad.tail1234.ts.net"
```

Sign in and open the panel:

```sh
komrad login --engine remote
komrad open --engine remote
```

## Connecting the forge

From your laptop, run <Command path="forge connect" args="github.com --method github-app --engine remote" />. The server mints its own tokens from the App's key, so you have nothing to paste. To connect GitLab too, follow [forge credentials](../forge-credentials/#gitlab).

[Runbooks](../runbooks/) covers running the engine from here on, up to [tearing it down](../runbooks/#tearing-it-down).
