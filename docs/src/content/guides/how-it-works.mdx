This guide gives a general overview of how komrad's different pieces fit together.

## The Different Services

Komrad is a server and a panel. The server runs in the background. It owns the database, answers the API, and watches every agent. The server, with its database, tmux and agents, makes up an engine.

The panel is just the UI.

Each agent is a real terminal running Claude or Codex. Komrad runs them in a tmux server of its own, so they never get mixed up with your own windows. When you open the panel, your terminal attaches to komrad's session. Closing the panel detaches that terminal and nothing else.

Everything goes through one API. The panel uses it. A script using <Command path="rpc" /> uses it. An agent calling an MCP tool uses it. All of them get the same rules and the same checks.

The commands, the tools, and the [API reference](../../api/) are all built from this single API definition.

## The State (Postgres)

All of komrad's state is kept in Postgres: a workflow, a task, an agent, a piece of mail, a review, and so forth. For external state, it uses a system of reconcilation, where "loops" find state from outside, such as pull request information or the idle state of a CLI, and sync that into Postgres.

Those changes are periodically _pushed_ to the client via a database triggers, a `LISTEN/NOTIFY` pattern, and a streaming ConnectRPC endpoint.

<figure>
  <img
    src={link("/diagrams/data-flow.png")}
    alt="A key press reaches the panel's Update, which returns a Cmd that calls the API over Connect RPC. The API handler passes it to the business logic, and the store commits the rows to Postgres, as the sync loops do too. On commit a trigger calls pg_notify with the table and key. The listener collects the changed IDs, and the reconciler streams the new rows over the Watch stream to Update, which changes the Model that View draws."
  />
</figure>

When the database detects a write on any table, it fires an event with the record's ID to a simple listener service.

In the server, those events arrive in a reconciler that is responsible for determining active state (including tombstones) for the application, and which then streams that information back to the client.

This pattern is always enforced. For instance, when the UI makes a POST call to the backend, it doesn't manually update it's own state with the response. Rather, the reconciler pattern streams the new state back through the UI's rendering pattern once the database has committed the changes.

This approach is designed to fit into BubbleTea's ELM architecture, and make parallelization of editors easier. Because state only ever flows through the system in one direction, diagnosing and fixing rendering issues is straightforward.

It also keeps the application lightweight. Komrad uses far less memory, in fact, than the coding CLIs it is orchestrating, making it a great, performant alternative to other agent frameworks.
