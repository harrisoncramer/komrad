Komrad's engine runs on one disposable Linux machine. Everything that has to outlive it sits on a separate data volume or in the database, so Terraform can replace the machine at any time. Any agents running at the time stop, and you resume them once the new machine is up.

## The image

Packer builds the image from the template in [`packer`](https://github.com/harrisoncramer/komrad/tree/main/packer). It starts from Ubuntu and installs Caddy, komrad and the tools the agents use, including git, tmux, Docker, Go, Node and the agent CLIs. Each layer is a short shell script, so adding a tool means adding a script.

The image carries a komrad binary so the server can start on first boot, before any deploy has run. Each deploy replaces that binary, which means the image only needs rebuilding when a tool or a boot step changes. [Deploys](../deploys/#image-updates) covers image updates.

## The komrad account

The server and every agent run as an account named komrad, which can't become root. Agents run whatever commands they decide to run, and the account keeps those commands away from the system and from the instance's AWS credentials. Those credentials come from the instance metadata service, and a firewall rule lets only root reach it. Docker runs rootless under the komrad account, so agents can still build and run containers.

Deploys, restarts and access grants need root, and they reach the machine through AWS Systems Manager. [Access](../engine-access/#operator-and-ci-access) covers that path.

## The data volume

The data volume holds the komrad account's home directory, which has komrad's config and the agent CLIs' logins. Every agent's worktree is on it too, along with komrad's cache and log and Caddy's certificates. When Terraform replaces the machine, the volume moves to the new one.

Terraform hands the machine a short user data script. The script records which volume, database and domain belong to the machine. It writes the identity provider into the server's config and points Caddy at the public listener. Any process on the machine can read user data, so the script carries nothing that has to stay secret. The provider's client secret is in it, but the engine hands that to every laptop that signs in anyway.

Systemd starts everything else in order. The data volume mounts first, and every unit that uses it waits for the mount. If the volume is missing, the server never starts, which keeps it from writing to the root disk by mistake.

Once the volume is up, the credentials unit reads the database owner's password from Secrets Manager, runs the migrations and writes the server's connection string. Alongside it, the GitHub key unit copies the App's private key from Secrets Manager into memory. The server starts after both have finished, and komrad then creates the tmux session the agents run in. Caddy waits only for the volume, since its certificates are stored there.

An hourly timer reruns the credentials unit, so the machine picks up the owner's new password after RDS rotates it.

## Agents during server restarts

The komrad server starts the tmux server that holds the agents, so tmux runs inside the server's systemd service. Left to its defaults, systemd would kill tmux whenever the server stopped. The server's unit tells systemd to stop only the server process, so a restart or a deploy leaves tmux and the agents running, and the new server picks them up.

Stopping or replacing the machine does stop every agent. Their conversations and worktrees stay on the volume, and you can resume them once the engine is back.
