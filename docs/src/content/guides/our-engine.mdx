Komrad's own development runs on one remote engine on AWS. The Terraform in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine) and the Packer template in [`packer`](https://github.com/harrisoncramer/komrad/tree/main/packer) build it. An engine doesn't need AWS. This guide describes one way to provide [the parts every engine needs](../running-komrad/).

One EC2 instance runs Caddy, the server and every agent. It boots from an image we build with Packer, which has every tool the agents use already installed. [The machine](../engine-machine/) covers the image and the boot.

A separate EBS volume holds the worktrees, the agent CLIs' logins and komrad's config. When we replace the instance, the volume moves to the new one. An Elastic IP keeps the instance's address across replacements, and the engine's domain points at that address.

RDS runs Postgres in private subnets that only the instance can reach. RDS manages the owner's password, keeps it in Secrets Manager, and keeps a week of backups. [The database](../engine-database/) covers how the instance gets its credentials.

Secrets Manager also holds the GitHub App's private key. The instance's role can read that key and the database's secret, and nothing else in Secrets Manager.

## Network access

The security group opens ports 443 and 80, and Caddy answers on both. Port 443 serves the engine. Port 80 serves Let's Encrypt's certificate check and redirects everything else to HTTPS. [Access](../engine-access/) covers how the engine checks each request.

No port is open for SSH. Operators open shells through AWS Systems Manager, which reaches the instance through the SSM agent on it. Deploys and restarts use Systems Manager too.

## GitHub Actions

GitHub Actions deploys releases, builds images, and stops and starts the instance. It holds no AWS keys. Each run gets a token from GitHub, and AWS exchanges that token for short-lived credentials on a CI role. The role trusts only this repository's branches and version tags, so a pull request from a fork can't use it.

The CI role can read Terraform's state, upload a binary to the state bucket, send commands to the instance through Systems Manager, stop and start the instance, and build images. It can't open an interactive session.

## Cost

The instance accounts for most of the cost, and it bills by the hour. A scheduled workflow stops it every night and starts it every morning. The volume, the database and the Elastic IP still bill while it's stopped. [Runbooks](../runbooks/#stopping-and-starting) covers stopping and starting it by hand.

## Terraform state

The engine stack and [the docs site](../docs-site/) stack keep their Terraform state in the same S3 bucket under different keys. We run Terraform through mise tasks, such as `mise run infra:engine:plan`, which select the right directory and backend.

The backend and variables files name an account's bucket, addresses and keys, so they aren't in the repository. Each has an example file beside it to copy.
