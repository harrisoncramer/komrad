Komrad's own development runs on one remote engine on AWS. This guide walks through how we put it together, and how it lines up with [the pieces every engine needs](../running-komrad/). The Terraform in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine) and the Packer template in [`packer`](https://github.com/harrisoncramer/komrad/tree/main/packer) build exactly what's described here, so you're welcome to copy them. You don't need AWS to run an engine, though. It just happens to be what we use.

## The machine

The whole engine runs on a single EC2 instance, booted from an image we build with Packer. The image comes with everything the agents need already installed, so a new instance is ready to work as soon as it boots. [The machine](../engine-machine/) covers what's in it.

We treat the instance itself as disposable. The worktrees, the CLIs' logins and komrad's config all live on a separate volume, which moves over to the new instance whenever we replace it. The instance also keeps a fixed address that survives a rebuild, and the engine's domain points at it, so nobody has to change anything on their end when the machine changes underneath them.

## The database

Postgres runs on RDS, off the machine and out of reach of everything but the instance. Keeping it separate means we can replace the instance as often as we like without worrying about the data. RDS also takes care of backups and the owner's password for us. [The database](../engine-database/) covers how the machine gets its credentials.

## Getting in

People reach the engine over HTTPS and sign in with their identity provider, as [access](../engine-access/) describes. Caddy runs on the instance to hold the certificate. It answers on the usual web ports, and nothing else on the machine is open to the internet.

There's no SSH. When we need a shell, or when GitHub Actions needs to deploy, we go through AWS Systems Manager instead. It needs no open port and no keys on the machine, and it ties every session to someone's AWS credentials.

GitHub Actions never holds an AWS key either. Each run gets short-lived credentials by proving to AWS that it's a workflow from this repository, so a pull request from a fork can't touch the engine.

## Keeping the bill down

The instance makes up most of the cost, and it bills by the hour. Nobody needs agents running at three in the morning, so a scheduled workflow stops the instance every night and starts it again in the morning. Everything on the volume and in the database stays put while it's off. [Runbooks](../runbooks/#stopping-and-starting) covers stopping and starting it by hand.

## Terraform

Both of our Terraform stacks, this one and [the docs site](../docs-site/), keep their state in the same S3 bucket. We never run `terraform` directly. Each stack has a group of mise tasks, such as `mise run infra:engine:plan`, that point it at the right directory and backend.

Your bucket, addresses and account details don't belong in the repository, so the backend and variables files aren't checked in. Each has an example next to it to copy.
