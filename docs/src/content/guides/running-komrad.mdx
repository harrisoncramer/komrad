This guide is for whoever runs komrad, rather than whoever uses it. It names every piece an engine needs and what each one holds. Nothing here depends on a cloud provider. [Our engine](../our-engine/) and the guides after it describe the one we run on AWS, as one way to put these pieces together.

## The pieces

<figure>
  <img
    src={link("/diagrams/running-komrad.png")}
    alt="The panel on your laptop signs in with an identity provider and reaches the engine host over HTTPS. An HTTPS front passes requests to the server, which runs agents in tmux. The agents keep their work on a disk and reach the forge with git. The server uses Postgres."

</figure>

An engine is a server, the agents it runs, and the database it writes. The panel is a separate process, and it usually runs on your laptop.

The server is <Command path="serve" />. It is the same komrad binary as the panel. It listens on two loopback addresses. The first is for the agents and the CLI on the same machine. The second is for people, and it checks every request for a sign-in and an access grant. Neither is reachable from the network on its own.

An HTTPS front sits in front of the second listener. It holds the engine's certificate, ends TLS, and passes each request through over loopback. We use Caddy, which gets and renews its own certificate. Any reverse proxy that carries HTTP/2 works.

An identity provider decides who people are. Google, Okta, Microsoft Entra and Keycloak all work, since each speaks OpenID Connect. People sign in there, with whatever MFA it asks for, and the panel sends the token it hands back with every request. Komrad never sees a password.

Postgres holds every record: workflows, tasks, agents, mail, reviews, transcripts, and who may use each engine. We run Postgres 18, and komrad uses three logins on it. [The database](../engine-database/) covers them.

Tmux runs the agents. Komrad starts a tmux server of its own, on its own socket, and every agent is a window in it. The server can restart without touching tmux, which is how agents survive a deploy.

The agent CLIs are Claude Code and Codex. Each has to be installed and signed in on the engine host, by the account komrad runs as.

A disk holds the worktrees agents edit, the CLIs' logins, komrad's config, its cache and its log. On a laptop that is your home directory. On a machine of its own it should be a volume that outlives the machine.

Forge credentials let agents push and komrad read pull requests. A personal token is fine on a laptop. A shared machine should use something that expires, as [forge credentials](../forge-credentials/) explains.

## Two shapes

  <img
    src={link("/diagrams/engine-shapes.png")}

  />
</figure>

On a laptop everything sits on one machine. [Installing komrad](../install/) covers it, and there is nothing to deploy beyond Postgres. Nobody else reaches it, so it needs no front and no sign-in.

A remote engine moves the server, the agents and the disk to a machine that stays on. The panel stays on your laptop and reaches the engine at an HTTPS address. Postgres can sit on the same machine, but a managed database survives the machine being replaced. [Remote engines](../remote/) covers using one.

Several engines can share one database. Each connects as its own login, and Postgres keeps each engine's rows out of the others' reach.

## What survives what

A remote engine is safe to restart, stop and rebuild, as long as the disk and the database live apart from the machine.

| Piece     | Holds                     | Server restart | Machine stop    | Machine rebuild |
| --------- | ------------------------- | -------------- | --------------- | --------------- |
| Server    | Nothing of its own        | Restarts       | Stops           | Replaced        |
| Agents    | Running CLIs              | Keep running   | Stop, resumable | Stop, resumable |
| Postgres  | Every record              | Kept           | Kept            | Kept            |
| Disk      | Worktrees, logins, config | Kept           | Kept            | Kept            |
| Root disk | The installed tools       | Kept           | Kept            | Replaced        |

An agent that stops keeps its conversation and its worktree, so you resume it once the engine is back. People stay signed in through all of it, since each person's sign-in lives on their own laptop.

## What to set up

To run an engine somewhere other than a laptop, you need:

- A Linux machine with tmux, git, the agent CLIs, and the komrad binary, running <Command path="serve" /> as a service under an account that cannot become root.
- A tmux session made at boot with <Command path="open" args="--headless" />, since nobody opens a panel on a machine with no screen.
- A Postgres it can reach, migrated with <Command path="migrate" />, and an engine login made with <Command path="engine ensure" />.
- A volume for the account's home and the worktrees.
- A domain name, and an HTTPS front on ports 80 and 443 with nothing else listening.
- An identity provider with komrad registered on it, and a grant for each person allowed in.
- A way for whoever runs the machine to get a root shell that isn't open to the internet.
- Forge credentials for agents to push with.

Set <Setting path="harness.claude.trust_launch_dirs" label="trust_launch_dirs" /> for each CLI, so a new agent in a fresh worktree doesn't stop to ask whether to trust it.

[Standing up an engine](../standing-up-an-engine/) walks through all of this for our AWS setup.
