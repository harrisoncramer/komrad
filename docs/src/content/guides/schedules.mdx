Let's say you want an agent to read overnight alerts every day at 10am and write up a summary for you. You can do this with schedules.

A schedule fires on a cron expression and hands its prompt to an agent. Schedules live in komrad's database, so they survive application restarts. There are two kinds.

An implementer schedule spawns a new implementer agent into a workflow each time it fires, with the schedule's prompt. Everything else about the launch, such as the directory, the flags and the shared context, comes from the workflow at the moment it fires.

An orchestrator schedule mails its prompt to an orchestrator that is already running. Use it when the work belongs to an agent that already knows the workflow, such as asking an orchestrator each morning to hand out the day's work. The mail is signed with the schedule's name and the orchestrator reads it as coming from you.

To create one, press `S` to open the schedules screen, then press `c`. Pick the kind first. An implementer schedule asks which workflow to launch into, and an orchestrator schedule asks which orchestrator to mail. The orchestrator kind is only offered while at least one orchestrator is running.

## How schedules work

Komrad never catches up on missed runs. If the service is down when a run was due, that run is skipped. This is intentional, to avoid agents running at odd hours.

An implementer schedule never piles up work. If an agent from its last run is still working or waiting on you, the next run is skipped and recorded as skipped. Plan accordingly.

Runs that cannot succeed are cancelled with a reason, which shows as the schedule's last run. An implementer schedule whose workflow no longer exists is cancelled. So is an orchestrator schedule whose orchestrator has been archived or deleted. Point the schedule at a new orchestrator, or archive it.

You can pause a schedule, which stops it firing until you arm it again.
