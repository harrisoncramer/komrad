Agents perform work in komrad. Each one is a real Claude or Codex session running in a terminal that komrad manages for you. Agents are designed to be stateless in komrad, so that you can easily create or discard them without losing work.

<Alert variant="warning">This guide assumes you know what a [workflow](../workflows/) and a [task](../tasks/) are.</Alert>

They are also durable. You can shut down or restart your machine without losing any history or context with an agent, and easily restore or search through their conversations later. Agents can also start and manage other agents.

## Three kinds of agent

Komrad has three kinds of agents.

There is always one _orchestrator_ agent per [workflow](../workflows/#the-orchestrator), which coordinates tasks and their agents.

An _implementer_ does a task's work. It makes edits, commits, and opens the pull request. Only one live implementer at a time holds a task's checkout, and komrad calls it the task's [writer](../tasks/#managing-task-agents). You can [hand off](../tasks/#handing-off) the work to a new writer whenever you want.

Finally, _reviewer_ agents read the writer's change and comment on it. Only the writer can ask for one. A reviewer is the writer's child: it works in the writer's checkout, makes no changes of its own, and is archived along with the writer.

```
  workflow (and its orchestrator)
   |
   |-- task: fix-login
   |      |-- writer        <-- an implementer, owns the checkout
   |      '-- reviewer      <-- the writer's child, reads its change
   |
   '-- task: rfc-truncate
          '-- writer
```

The list draws the same tree. Each workflow row holds its tasks, and each task lists every agent on it. The writer's children sit beside it under the task, drawn in the child style, so you can tell them apart from the writer.

## Starting agents

Most of the time you start an agent by [starting a task](../tasks/#starting-a-task), which launches its first implementer. The other way is to ask the orchestrator. Tell it what you want done and it creates the tasks, puts an implementer on each, and writes each one a brief.

## Reviewers

The writer asks for a review when it thinks its work is ready, and komrad starts a reviewer as its child. The reviewer reads the change and leaves comments on its lines, the same way you do in a [review](../reviews/), and the writer answers them. While a reviewer is still reading and has not approved, the writer cannot ask for another. Over a task's life it can go through many.

Neither you nor the orchestrator starts reviewers directly. Starting a new agent on a task from its menu with <Key name="menu.new_agent" /> while it has a live writer does not make a reviewer. It makes a plain child of the writer: a helper that runs in the writer's checkout with only the brief you give it, cannot ask for a review, and is archived with the writer. Use it for side work such as answering a question about the change. Keep the writing itself with the writer, since a child that edits the checkout works under the writer's feet.

Set <Setting path="usage.implementer.max_children" /> to cap how many children, reviewers included, one writer can hold at a time.

## Adopting work

Sometimes the work started outside komrad, such as a colleague's pull request or a branch you began on another machine. Hover the workflow, open the menu with <Key name="menu.open" /> and press <Key name="menu.adopt" />. Name the branch and say what to do with it. Komrad starts a task on that branch with an implementer as its writer, in a worktree of its own when the workflow cuts them.

The branch has to be in the workflow's repository, either pushed to its origin or already on disk.

## Archiving and deleting an agent

Archiving an agent stops it and takes it out of the list. Its conversation stays in the database, so you can still search it or restore it later. Archiving a writer archives its children too, reviewers included, and archiving the last live agent on a task archives the task.

Deleting an archived agent is permanent and removes its conversation. Its task, with the worktree and reviews, stays until the task itself is [deleted](../tasks/#archiving-restoring-and-deleting-tasks).

## How komrad knows what an agent is doing

Most agent tools learn what an agent is doing from hooks the agent fires. Hooks can be dropped, reordered, or never sent, for example when the CLI crashes. When that happens, those tools show an agent as working when it is idle, or waiting when it is done.

Komrad reads each agent's state from what its terminal actually shows, which komrad calls the pane. The [Claude test panes](https://github.com/harrisoncramer/komrad/tree/main/internal/harness/claude/testdata) show what it reads.

This has a cost. If a process dies, komrad still sees it, but a new release of Claude or Codex that draws its screen differently can confuse it. If Claude or Codex ever ship real-time state notifications, komrad will move to them. Until then, reading the pane is the more reliable choice.

If the state shown does not match your CLI, please <a href={link('/guides/bug-reports')}>submit an issue</a> on GitHub.
