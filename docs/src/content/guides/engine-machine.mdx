Our engine runs on one Linux machine. Anything that must survive lives on a separate data volume or in the database, so we can replace the machine at any time. Replacing it stops the agents that were running, and they can be resumed afterwards.

## The image

Packer builds the image from the template in [`packer`](https://github.com/harrisoncramer/komrad/tree/main/packer). It starts from Ubuntu and installs git, tmux, Docker, Go, Node, the agent CLIs, Caddy and komrad. Each layer is a short shell script.

The image includes a komrad binary so the machine can start the server on first boot. Every deploy replaces that binary, so the image only needs rebuilding when a tool or a boot step changes. [Releases and deploys](../deploys/#image-updates) covers that.

## The komrad account

The server and every agent run as an account named komrad, which can't become root. Agents run whatever commands they choose, so this account can't change the system or read the instance's AWS credentials. A firewall rule blocks every account except root from the instance metadata service, which serves those credentials. Docker runs rootless under the komrad account, so agents can build and run containers without root.

Root work, such as deploys, restarts and access grants, comes in through AWS Systems Manager. Nobody logs in over SSH. [Access](../engine-access/) covers it.

## The data volume

The data volume holds the komrad account's home directory, with komrad's config and the agent CLIs' logins. It also holds every agent's worktree, komrad's cache and log, and Caddy's certificates. When we replace the machine, the volume moves to the new one with all of this on it.

Terraform passes the machine a short user data script. The script records which volume, database and domain belong to this machine, and writes Caddy's config. It holds no secrets, because any process on the machine can read user data.

Systemd then starts the units in order. The data volume mounts first. Every unit that uses the volume waits for it, so a missing volume stops the server instead of letting it write to the root disk.

Next, the credentials unit reads the database owner's password from Secrets Manager, migrates the database, and writes the server's connection string. The GitHub key unit copies the App's private key from Secrets Manager into memory. The server starts after both finish. Then komrad creates the tmux session the agents run in. Caddy starts once the volume is mounted, since its certificates live there.

An hourly timer reruns the credentials unit. That picks up the owner's new password after RDS rotates it.

## Agents during server restarts

The server starts the tmux server that holds the agents. By default, systemd would stop tmux along with the server, since tmux runs inside the server's service. The server's unit tells systemd to stop only the server process. A restart or a deploy leaves tmux and every agent running, and the new server picks them up.

Stopping or replacing the machine stops every agent. Their conversations and worktrees stay on the volume, so they can be resumed once the engine is back.
