One of the hardest parts of working with agentic development tools is keeping a handle on the massive amount of code they can produce.

Komrad aims to make reviewing easy though it's review panel.

With it, you can comment on changes and reply to the agent implementing a feature. You can also see the specific edit the agent made in response to a comment, step back through the history of the changes, and even see and reply to comments from a colleague on your changes.

## Local reviews

While a change is still taking shape, iterating with the agent directly is often faster than pushing to a forge like GitHub or GitLab.

Komrad supports this with _local reviews_. You read the task's diff, leave comments on its lines, and edit it yourself, and the writer answers in the same view. That keeps feedback loops quick and saves CI runs on work that isn't ready yet.

<Alert variant="info">Local reviews are completely optional, you can use komrad without them.</Alert>

Komrad's local review model resembles <a href="https://www.gerritcodereview.com/">Gerrit</a>'s code review. You step through the change in rounds, and each round holds the code as it stood when it was reviewed.

### Opening a review

Hover the task, open its menu with <Key name="menu.open" />, and pick review with <Key name="menu.review" />. The main view shows everything the task's branch changed since it left the base.

The sidebar holds a tree of the files the change touches, and the main view holds the diff and the conversation.

The sidebar also lists what waits on you. It shows replies you have not read, forge comments to pass on, and drafts you have not sent. Move the cursor onto one and press <Key name="review.toggle_folder" /> to go to its thread. When the task has a pull request, the sidebar also shows the forge's review decision, who commented there, and the pull request's title. Press <Key name="review.toggle_folder" /> on the title to read the description.

### Leaving comments

Open the review's menu with <Key name="menu.open" /> on a line and press <Key name="review.compose" /> to comment on it.

A comment stays a draft until you send your review, as on GitHub or GitLab. A draft stays on its line while the writer keeps working, and the sidebar says when the code under it changes.

### Editing the code yourself

Sometimes fixing a line is quicker than describing the fix. Open the menu and press <Key name="review.edit_file" /> to open the file in your editor (the `$EDITOR` in your terminal, like vim) beside the diff. Komrad pauses the writer while you edit, since you both work in the task's checkout. When you close the editor, the writer carries on from your change.

### Sending

When you are done reading, open the menu and press <Key name="review.send" /> to send the review. Komrad asks if you have anything to say about the work as a whole, then sends it to the task's writer. Sending stops the writer mid-turn, so it reads your comments now instead of when it finishes what it is doing.

Each comment goes out with the lines it was written on and the code around them, so the writer can find the spot even after the file has moved.

The writer answers in your threads and can settle them. To see exactly what it changed in answer to a comment, open the thread's menu and press <Key name="review.answer" />. You can settle or reopen any thread yourself.

### Stepping through history

Each review you send is written against the round you read. Press <Key name="review.base" /> to step back from the whole change to the work since your last review, and on through your older reviews. Press <Key name="review.base_forward" /> to step forward again. The top of the diff names the rounds on screen, such as round 1 to round 2.

A range that ends before the newest round takes replies but not new comments, because new comments go on the newest round.

### Reviews from agents

The writer can ask for a [reviewer](../agents/#reviewers) when it thinks its work is ready, and you can start one yourself from the task's menu. A task can hold more than one reviewer at once, up to <Setting path="usage.task.max_reviewers" />. A reviewer reviews the same way you do, leaving threads on the task's diff and releasing a review the writer answers.

A review hides a reviewer's threads when it opens, so you see your own first. Open the review's menu and press <Key name="review.agent_threads" /> to show or hide them.

## Shipping the work

Once you're happy with the change locally, it goes to a forge, like GitHub or GitLab.

<Alert variant="info">
  Connect a forge before agents can push or komrad can follow pull requests. [Connecting a
  forge](../install/#connecting-a-forge) covers GitHub and GitLab.
</Alert>

### Pushing and opening the pull request

The writer commits, pushes its branch and opens the pull request itself, so the simplest path is to tell it to. You can also push from the task's git menu: open the task's menu, press <Key name="menu.git" />, then <Key name="git.push" />. Komrad says how many commits go up before it pushes.

Komrad links a pull request to a task by its branch, so a pull request opened from the task's branch shows up on the task's row on its own. The git menu then opens it in your browser with <Key name="git.open_pull_request" />.

### Following the pull request

While any agent on a task is live, komrad follows its pull request. It notices when checks pass or fail, when it is approved, and when it is merged, and shows that as a symbol on the task's row. Some of those changes also [tell the writer](../events-and-messages/#events-and-mail), such as checks failing or the branch conflicting with its base.

Komrad reads a repository every five seconds when something there is likely to change soon, such as checks still running, a branch that just moved, or a pull request komrad just wrote to. It reads every other repository once a minute. When the forge says little of the hour's budget is left, komrad drops every repository on that host to once a minute until the budget comes back.

### Syncing comments from Github or Gitlab

Komrad also reads the review comments on each followed pull request or merge request, drafts included, once a minute. Each one is copied into the task's review as a thread of its own. Press <Key name="review.next_thread" /> to move to the next thread and read it out. A reply or an edit on the forge lands in the same thread, and resolving one there resolves it here.

Comments from someone who can push to the repository reach the writer on their own. Komrad holds comments from anyone else until you send your review or reply in their thread, so nothing from a stranger reaches the writer before you see it.

The writer answers forge comments in the review, never on the forge itself, and komrad never writes anything back to the forge.

### Merging

When the pull request is ready, open the task's git menu and press <Key name="git.merge" /> for the merge menu. You can merge and leave the task where it is, merge and archive the task, have the forge merge it on its own once checks and reviews pass, or merge and then rebase the task's worktree onto the base so the writer can start its next change.

### Cleaning up

A merged task can be archived, which stops its agents and keeps everything else, or deleted, which also removes its worktree. [A task's life](../tasks/#archiving-restoring-and-deleting-tasks) covers both. Merge and archive does the first step for you.

## Credentials

### Where the token lives

The database holds only which forge and which account. The token itself sits in a file only your user can read, and never shows up in logs. The GitHub CLI and your SSH keys work the same way.

Agents never hold a credential of their own, and no token is ever typed into a pane, so none can leak into a transcript. Komrad hands each tool the credential when the tool runs.

On your laptop, `gh` gets a token from the App when <Setting path="github_app" label="[github_app]" /> is set, and otherwise uses the login `gh` already has. Git uses whatever credential you already have. On a remote engine, git and `gh` hold a placeholder, and the control plane adds the person's GitHub login, as [komrad's engine](../komrads-engine/#forge-credentials) describes.

For GitLab, `glab` gets the token of the connection for the checkout's host, in a config that names that host alone, so the token is never sent anywhere else. With no connection for that host, it uses the login `glab` already has. Git reaches GitLab through <Command path="gitlab credential" /> once you add a line for each host.

```sh
git config --global credential.https://gitlab.example.com.helper '!komrad gitlab credential'
```
