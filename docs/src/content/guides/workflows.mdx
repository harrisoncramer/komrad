Komrad agents run inside _workflows_. Every agent belongs to one workflow, which provides common, editable settings to every agent spawned within it.

<Alert variant="warning" >
    This guide assumes you have [installed komrad](../install/) already.
</Alert>

Think of a workflow as the container for agroup of agents that do the same kind of work.

## Creating one

Let's set up a dummy repository, so that the workflow can spawn agents into it:

```sh
mkdir ~/learning-komrad
cd ~/learning-komrad
git init
```

Then run `komrad open` and press `w` in the panel, name the workflow `learning-komrad` and submit it with `<C-s>` to create it.

## What a workflow decides

Workflows control where agents start, which CLI they run, and what flags they are launched with, such as the model. When you spawn an agent you can override any of these for that one agent.

Think of a workflow as an editable set of presets for every agent that spawns within it. Changing the workflow only affects agents spawned afterwards; existing agents are unaffected.

## Shared context

Workflows can hold shared text that are included in every agent's system prompt. This is where you put what you would otherwise tell each agent by hand: how tests run, and how branches are named.

It comes after komrad's own briefing and your [global context](../../config/#context).

## Worktrees

Agents that write code need to stay out of each other's way. Komrad can automatically create a worktree for each agent, which is cut fresh from a base branch. The agent works on a branch of its own, and the worktree is removed when the agent is deleted.

The workflow's directory has to be an ordinary clone for this to work.

Worktrees go in [`worktrees.dir`](../../config/#worktrees.dir) unless the workflow names its own location. Each worktree is a clean checkout, so a workflow can list files to copy in, like local environment files, or local packages. For anything heavier, like installing or networking configuration, use a [hook](../hooks/) instead.

<Alert variant="info" >
    Agents do not have to create worktrees, but be careful: those that do not will run directly inside of the directory specified.
</Alert>

The worktree's branch is worked out from your repository's clone when you create the workflow. New worktrees are cut from it and an agent's work is measured against it. If the clone loses that branch, `komrad doctor` says so.

## Archiving and restoring

Archiving a workflow puts it into cold storage: you can hard-delete it later, but for now, it'll be hidden from your workflow view.

Nothing is destroyed, and search still finds what the agents said. However, the agents inside of the workflow will be shut down. Restoring brings the whole workflow back, along with its agents in a stopped state, and ready to resume.

## Next Steps

You don't have to build your entire workflow right away.

Start with a directory and a worktree setting. Add context later. You can always have multiple workflows in the same directory, for instance, for different purposes like bugfixing or feature work.
