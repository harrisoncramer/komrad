This guide builds [our engine](../our-engine/) from an empty AWS account. It runs top to bottom, and nearly every step is a mise task you run from a komrad checkout. The tasks use the AWS profile named komrad, unless your environment already has credentials in it.

## Before you start

A few things need to exist before you build anything.

On the AWS side, you'll want an account with a named profile, an S3 bucket for Terraform's state, and the Session Manager plugin for the AWS CLI. The machine has no SSH, so the plugin is how you'll get a shell on it.

You'll also need a domain for the engine at a DNS host you control, such as `komrad.example.com`, and komrad registered with your identity provider as a desktop app. [Access](../engine-access/#registering-komrad-with-the-provider) explains the registration. Hold on to the client id it gives you.

Last, the engine needs a GitHub App to push as. [Forge credentials](../forge-credentials/) covers registering it. Put its private key in Secrets Manager before the machine first boots, so the machine finds it waiting.

## Build the image

```sh
mise run packer:build
```

This builds the machine's image with every tool the engine needs, and prints its id when it's done. [The machine](../engine-machine/) covers what goes in it.

## Apply the infrastructure

Copy `terraform.tfvars.example` and `backend.hcl.example` in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine), drop the `.example`, and fill them in. Among other things they name your account, the image you just built, and the engine's domain. Then:

```sh
mise run infra:engine:init
mise run infra:engine:apply
```

When the apply finishes, it prints the engine's address. Add an A record for your domain pointing at it. We leave DNS to you on purpose, so the engine doesn't depend on any particular DNS provider. Once the record resolves, Caddy fetches a certificate on its own.

The machine sets itself up on first boot. To check it went well, open a session and look for anything that failed:

```sh
aws ssm start-session --target i-0123456789abcdef0
systemctl list-units --state=failed --no-legend
```

## Wire up GitHub Actions

Releases and the nightly schedule reach the engine from GitHub Actions, so the repository needs to know where it is. Set these repository variables:

- `AWS_CI_ROLE`, from the apply's `ci_role_arn` output
- `AWS_REGION`
- `TF_STATE_BUCKET`
- `TF_STATE_KEY`, matching the key in your backend file

If you renamed the stack, set `ENGINE_NAME` to match, too. Until `AWS_CI_ROLE` is set, the workflows just skip their engine steps.

## Configure the engine

In your session on the machine, switch to the account komrad runs as:

```sh
sudo -u komrad -i
```

Open `~/.config/komrad/config.toml` and tell it about your identity provider and komrad's client id there. Add the <Setting path="github_app" label="[github_app]" /> table with your App's details, and turn on <Setting path="harness.claude.trust_launch_dirs" label="trust_launch_dirs" /> for each agent CLI, so new agents don't stop to ask whether they trust their worktree. <Command path="github token" /> should print a token once the App is set up. Then restart the server so it picks up the changes, as [runbooks](../runbooks/#restarting) shows.

While you're still the komrad account, start each agent CLI once and sign it in, and clone the repositories you want agents to work in. All of it lives on the data volume, so you won't have to do it again after a rebuild.

## Let yourself in

Back in the session's own shell, grant yourself access:

```sh
sudo komrad-access grant you@example.com
```

On your laptop, tell komrad where the engine is with a file at `~/.config/komrad/engines/remote.toml`:

```toml
[connection]
url = "https://komrad.example.com"
```

Then sign in and open the panel:

```sh
komrad login --engine remote
komrad open --engine remote
```

## Connect the forge

Last of all, from your laptop, point the engine's GitHub connection at the App with <Command path="forge connect" args="github.com --method github-app --engine remote" />. The server mints its own tokens from the App's key, so there's nothing to paste. If agents also work on GitLab, [forge credentials](../forge-credentials/#gitlab) covers connecting it.

That's it. [Runbooks](../runbooks/) covers looking after the engine from here, all the way to [tearing it down](../runbooks/#tearing-it-down).
