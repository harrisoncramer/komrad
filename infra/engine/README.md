# Engine

One machine in AWS that runs the komrad server, with its own Postgres and a disk that outlives
the machine. The image it boots from is built separately by Packer under `packer/`.

```
                     you (SSH from allowed addresses)
                     GitHub Actions (SSM, no SSH)
                              |
                              v
   +---------------------- VPC ----------------------------+
   |                                                        |
   |   public subnet                                        |
   |   +------------------------------+                     |
   |   |  EC2 instance  (fixed IP)    |                     |
   |   |  komrad serve               |                     |
   |   |  /var/lib/komrad  <---------+---- EBS data volume |
   |   +--------------+---------------+       (encrypted,   |
   |                  |                        follows the  |
   |                  | 5432, only from         instance)   |
   |                  | the instance                        |
   |                  v                                     |
   |   private subnets                                      |
   |   +------------------------------+                     |
   |   |  RDS Postgres                |                     |
   |   |  password in Secrets Manager |                     |
   |   +------------------------------+                     |
   +--------------------------------------------------------+
```

## What is where

The instance sits in a public subnet with a fixed elastic IP, so its address survives a
replacement. Port 22 is open only to the addresses in `ssh_allowed_cidrs`. An empty list opens it to
nobody, and Terraform refuses `0.0.0.0/0`. CI never uses SSH. It sends commands through SSM,
which the instance role allows.

The database lives in private subnets with no public address. Its security group accepts
connections only from the instance's security group. Its password is generated by RDS and kept in
Secrets Manager, and the instance role can read it, so nothing in Terraform state or on disk
holds the password in plain text.

The data volume is a separate encrypted EBS disk mounted at `/var/lib/komrad`. It is attached to
the instance rather than part of it, which is the whole point: the instance can be thrown away
and the disk reattached to the next one.

## Replacing versus stopping

Changing `ami_id`, moving the database, or editing the boot script all replace the instance and
stop every agent on it. That is the upgrade path, not an accident. The data volume detaches and
follows the new host, and the root volume is discarded.

Stopping is different, and Terraform has no part in it. Terraform does not track whether the
instance is running, so a plan sees no drift against a stopped engine and an apply will not
start one. `mise run remote:stop` and `mise run remote:start` do that through the AWS CLI, and
the `engine start` and `engine stop` workflows run them on a schedule overnight.

`database_deletion_protection` defaults to true, so a destroy refuses until it is set false and
applied.

## How CI reaches it

GitHub Actions assumes the `<name>-ci` role, `komrad-development-ci` by default, using a token GitHub signs for each run. The
role trusts only this repository's branches and its `v` tags, so a fork cannot use it. The role
can read Terraform state to find the instance, send it an SSM command, start and stop it, and
build an image with Packer. It cannot log in.

The `engine` workflow puts a build on the instance. The `image` workflow builds a new AMI and
records its id in an SSM parameter, which is how `mise run remote:reimage` knows what to move to.

## Running it

Copy `terraform.tfvars.example` and `backend.hcl.example`, fill them in, then
`mise run infra:engine:init` and `mise run infra:engine:apply`. The full path from a built image
to a working panel is in `docs/src/content/guides/engine-admin.md`.
