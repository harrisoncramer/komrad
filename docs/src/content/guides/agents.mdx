Agents run your workloads. They are spawned according to workflows.

Komrad currently supports just Claude and Codex agents. You can leave them working and come back, restart your machine without losing any history or context, search everything they have said, and even have agents spawn and manage other agents.

This is the core value for komrad: _durable, resumable, searchable agentic compute_.

There are three types of agents, and you've already seen one: the [orchestrator](../workflows/#the-orchestrator). Orchestrator agents can spawn children called "implementer" agents, which each (typically) get their own worktree. Finally, implementer agents can spawn reviewer agents, which live inside _the same worktree_ and are responsible only for reviewing their work.

```
  workflow
   |
   '-- orchestrator                <-- one per workflow, coordinates work
           |
           |-- implementer         <-- multiple per orchestrator, writes code
           |       |
           |       '-- reviewer    <-- multiple per implementer, provides feedback
           |       |
           |       '-- reviewer
           |
           '-- implementer
                    |
                    '-- reviewer
```

The agent responds to our question. If it needs to, it can send and receive messages from the orchestrator.

Each agent is in one of several states, such as running, idle, dormant, or active. The state of the agent is reflected in the UI column.

Dorman agent's CLI have exited, but their conversations are kept so that you can still search them, and resume them later. You can search the agent list by name, filter it, jump around it with [marks](../../config/#keybindings.marks). Press <Key name="cycle.views" at={0} /> and <Key name="cycle.views" at={1} /> to cycle through the views: the sidebar, the agent's screen, and the info pane.

## Reviewer Agents

Reviewer agents are attached to an implementer agent, and can be used to review it's work. Don't try to have reviewer agents run work: each change should be implemented by an implementer agent, so that isolation between edits is guaranteed. ## Reviewer Agents

Reviewer agents share the implementer's checkout. They make no changes of their own, but provide feedback on their parent's chagnes. Set the [`usage.implementer.max_children`](../../config/#usage.implementer.max_children) value to cap how many reviewers one implementer may hold at a time.

## Adopting work

If you need to resume work that started outside of komrad (such as reviewing a pull request from a colleague, or resuming work from another machine) you can _adopt_ the branch. Adopting the branch lets komrad spawn an implementer agent into that branch responsible for resuming work on it.

To adopt a branch, press <Key name="workflows.adopt" /> when hovering over a workflow.

Because adoption creates a new implementer agent, the adopted branch must be available in the repository controlled by the workflow you are adopting work into.

## Tearing down

In komrad, you can either _archive_ or _delete_ an agent.

Archiving an agent will stop it immediately, and remove it from the agent sidebar. It will not remove its conversation from Postgres, so you can still search for it or resume it later.

Deleting an agent is permanent. When you choose to delete an agent, the conversation and the worktree are all removed.
