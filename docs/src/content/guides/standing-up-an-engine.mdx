This guide replicates [komrad's engine](../komrads-engine/) in an AWS account of your own. It builds the same architecture from an empty account, with each step in the order the later ones depend on, and then covers the routine jobs of running it. The Terraform, the Packer template and the mise tasks are the ones komrad's own engine runs on, so a different architecture means changing them first. Run every command from a komrad checkout. The mise tasks use the AWS profile named komrad unless your environment already has credentials.

## Prerequisites

A replica needs its own account with each service komrad's engine depends on:

- An AWS account with a named profile, and an S3 bucket for Terraform's state.
- An EC2 vCPU quota large enough for the control plane, every dev box, and as many workers as you plan to run at once.
- The Session Manager plugin for the AWS CLI, which you need to get a shell on the control plane or a box.
- A Tailscale tailnet you administer, with Tailscale running on your laptop.
- Komrad registered with your identity provider as a desktop app. [Komrad's engine](../komrads-engine/#provider-registration) covers the registration.
- A GitHub App for the bot, with its private key stored in Secrets Manager as `komrad/github-app`. [Credentials on an engine](../engine-credentials/#registering-the-app) covers the App. The control plane reads the key at boot, so store it before the first one.
- A GitHub OAuth app with device flow turned on, for people to authorize. Device flow uses its client id alone. Each organisation that restricts OAuth apps needs one of its owners to approve it before people's logins reach that organisation.
- An Anthropic organisation with a service account and a workspace for the bot.
- An OpenAI project with a service account for the bot, and an admin key for that project stored in Secrets Manager.

## Building the images

```sh
mise run packer:build
```

The build makes the control plane image and the box image, and prints each one's id when it finishes. Terraform needs both ids in a later step. Komrad's engine describes [the control plane image](../komrads-engine/#the-control-plane-image) and [the box image](../komrads-engine/#the-box-image).

## Preparing the tailnet

The control plane joins your tailnet as one tagged device, and the rest of the tailnet stays as it is. In Tailscale's admin console:

1. Under DNS, turn on MagicDNS and HTTPS certificates. The tailnet's DNS name, such as `tail1234.ts.net`, is at the top of the page.
2. In the access policy, add `tag:komrad-engine` to `tagOwners`, as [komrad's engine](../komrads-engine/#the-tailnet-policy) shows.
3. Under Settings, then Keys, generate an auth key. Make it single-use and pre-approved, and tag it `tag:komrad-engine`. The control plane uses it only to join the first time, so a key that expires in a day is enough.

## Making the signing key

The control plane signs identity assertions for Claude on workers with a key of its own. Make an RSA key pair, and store the private key in Secrets Manager. In the Anthropic Console, register the engine as an issuer with the public key pasted in, then add a federation rule that maps any subject starting with the engine's name to the bot's service account. Note the rule's id, the organisation's id, the service account's id and the workspace's id for the next step.

## Applying the infrastructure

Copy `terraform.tfvars.example` and `backend.hcl.example` in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine), remove the `.example`, and fill them in. The variables include your account, the region, both image ids, the subnets for each availability zone, and the `sign_in_*` values from your provider. Set `tailscale_hostname` to the engine's name on the tailnet, which defaults to komrad, and `tailscale_tailnet` to your tailnet's DNS name, such as `tail1234.ts.net`. Set `tailscale_auth_key` to the auth key from the earlier step, which Terraform stores in Secrets Manager for the control plane. Name the secrets that hold the signing key and the OpenAI admin key, so the control plane's role can read them. GitHub Actions needs the `github_*` values and `state_bucket` to deploy. Then run:

```sh
mise run infra:engine:init
mise run infra:engine:apply
```

The apply prints the engine's address as `engine_url`, the control plane's instance id as `instance_id`, and the CI role as `ci_role_arn`.

On first boot, the control plane joins the tailnet with the auth key, mounts its data volume, migrates the database, creates the engine's login, and starts the server and Caddy. The key is spent once it joins.

Open a session and check that no unit failed. On a healthy control plane the second command prints nothing:

```sh
aws ssm start-session --target i-0123456789abcdef0
systemctl list-units --state=failed --no-legend
```

## Configuring GitHub Actions

Komrad's release and image workflows deploy to its engine. In your copy of the repository, they reach your engine through these repository variables:

- `AWS_CI_ROLE`, from the `ci_role_arn` output
- `AWS_REGION`
- `TF_STATE_BUCKET`
- `TF_STATE_KEY`, matching the key in your backend file

If you changed the stack's `name`, set `ENGINE_NAME` to match. The workflows skip their engine steps until `AWS_CI_ROLE` is set.

## Configuring the engine

In a session on the control plane, switch to the komrad account, which owns komrad's config:

```sh
sudo -u komrad -i
```

Edit `~/.config/komrad/config.toml`:

- Add the <Setting path="github_app" label="[github_app]" /> table with the App's id and its installation id.
- Name the OAuth app's client id, so the panel can ask people to authorize GitHub.
- Name the federation rule, the organisation, the service account and the workspace from the signing key step, and the OpenAI project and its service account.
- Set the worker cap, the most workers the engine runs at once.
- Turn on <Setting path="harness.claude.trust_launch_dirs" label="trust_launch_dirs" /> for each agent CLI, so new agents trust their worktree as they start. The runner applies it on each box.

Then restart the server so it loads the new config, as [restarting](#restarting) shows.

Workers get model access from the control plane, and each person signs their own CLIs in on their dev box.

## Granting your own access

Exit the komrad account's shell and grant yourself access:

```sh
sudo komrad-access grant you@example.com
```

Check that your tailnet policy lets you reach the engine on 443. Then, on your laptop, create `~/.config/komrad/engines/remote.toml` with the `engine_url` the apply printed:

```toml
[connection]
url = "https://komrad.tail1234.ts.net"
```

Sign in and open the panel:

```sh
komrad login --engine remote
komrad open --engine remote
```

## Connecting the forge

From your laptop, run <Command path="forge connect" args="github.com --method github-app --engine remote" />. The server mints its own tokens from the App's key.

## Adding a dev box

Each person who works on the engine needs a grant and a dev box. Add the person to the dev boxes in `terraform.tfvars`, with the issuer and subject they sign in with and the box's size, and apply. A person's subject is in their ID token, which <Command path="token" /> prints once they have signed in.

The person then starts the box from the panel and authorizes GitHub when the panel asks. To remove a dev box, take the person out of `terraform.tfvars` and apply. Terraform deletes the box and its volume.

## Running the engine

These jobs keep komrad's engine running, and they work the same on a replica. Run them from a komrad checkout, with AWS credentials from the komrad profile or from your environment. The mise tasks look up the control plane and its region in Terraform's state.

### Getting a shell

You get a shell on the control plane through AWS Systems Manager, which needs the Session Manager plugin for the AWS CLI. Look up the instance's id in Terraform, then open a session:

```sh
mise run infra:engine:run output instance_id
aws ssm start-session --target i-0123456789abcdef0
```

The session runs as a user with sudo. Switch to the komrad account to work as the server does. That account owns the config and the hooks:

```sh
sudo -u komrad -i
```

`mise run remote:connect` opens the session and switches to the komrad account in one step.

A box takes a session the same way, with the box's instance id from the EC2 console. People reach their own dev box and bot workers through the SSH host [remote engines](../remote/#editing-files-on-the-engine) describes, so a session on a box is for operators.

### Checking engine health

When the engine's heartbeat stops, the dot beside its name in the panel turns red. Open a shell on the control plane and list the failed units. On a healthy control plane the command prints nothing:

```sh
systemctl list-units --state=failed --no-legend
```

Then look at Tailscale, the server and Caddy. `tailscale status` shows whether the control plane is on the tailnet. The journal shows what systemd saw, like a crash at startup or a certificate request that failed. Komrad's log shows what the server wrote while it ran.

```sh
sudo tailscale status
systemctl status tailscaled komrad caddy
journalctl -u tailscaled -n 200 --no-pager
journalctl -u komrad -n 200 --no-pager
journalctl -u caddy -n 200 --no-pager
tail -n 200 /var/lib/komrad/cache/komrad.log
```

The panel shows a box as stuck when its runner went back to its previous build after an update. The next deploy tries the update again.

### Sign-in failures

When the engine rejects someone's token, their panel asks them to sign in again:

```sh
komrad login --engine remote
```

If the engine still turns them away, they don't have a grant. Check that the email they signed in with is the one you granted, and that their provider has verified it.

If their panel says the engine is unreachable, check that Tailscale runs on their laptop with DNS on and that the tailnet policy lets them in.

### Rejoining the tailnet

A replaced control plane keeps its tailnet identity through Parameter Store. If someone removes the engine from Tailscale's admin console, it drops off the tailnet and needs a new key. Set `tailscale_auth_key` to a new single-use, pre-approved key tagged `tag:komrad-engine` and run `mise run infra:engine:apply`. Then join again in a shell on the control plane:

```sh
sudo systemctl restart komrad-tailscale
```

### Restarting

`mise run remote:restart` restarts the server. Agents keep running on their boxes, and every runner reconnects once the server is back. If the control plane is stopped, the task starts it instead.

People stay signed in through a restart, and their panels reconnect once the server is back.

### Deploying or rolling back

Releases deploy on their own. To deploy the build in your checkout, run `mise run remote:deploy`. One deploy updates the control plane, and every runner fetches the new build over its stream.

To roll back, deploy an older ref. Either check it out and run `mise run remote:deploy`, or, without AWS credentials, dispatch `engine.yml` from the Actions tab on the tag or branch you want. Runners follow the control plane back to the older build.

### Stopping and starting

```sh
mise run remote:stop
mise run remote:start
```

Stopping asks you to confirm, because it stops the control plane and every box, and every agent with them. The volumes, the database and the address stay. Starting waits until the control plane passes its health checks. Dev boxes stay stopped until their people start them, and workers start as their tasks are resumed.

### Moving to a new image

Dispatch `image.yml` from the Actions tab to build both images. Then run:

```sh
mise run remote:reimage
```

The task replaces the control plane with the new control plane image, and records the new box image for workers the control plane makes from then on. Agents keep running on their boxes through it. With no argument it uses the images `image.yml` recorded last. To use images you built yourself with `mise run packer:build`, pass their ids.

A worker keeps its image until its task is archived and restored. Dev boxes move to the new box image when you set its id in `terraform.tfvars` and apply. Terraform replaces each dev box and keeps its volume, so the person's agents stop and they resume them.

### Granting and revoking access

In a shell on the control plane:

```sh
sudo komrad-access grant someone@example.com
sudo komrad-access revoke someone@example.com
```

A person also needs to reach the engine over the tailnet. Check that your policy lets them reach it on 443, or share the engine with them from Tailscale's admin console if they're outside your tailnet. To give them workflows of their own, [add a dev box](#adding-a-dev-box).

[Komrad's engine](../komrads-engine/#access-grants) describes what a grant allows.

### Rotating credentials

[Credentials on an engine](../engine-credentials/) describes each key. The control plane reads its keys at boot, so each rotation that changes a secret ends with a server restart.

To rotate the GitHub App key, generate a new private key in the App's settings and store it in the `komrad/github-app` secret, under `private_key`. Restart the server, check that bot tasks can push, then delete the old key from the App.

To rotate the OpenAI admin key, create a new admin key for the project, store it in its secret, restart the server, then delete the old key in OpenAI. Keys the control plane already made for tasks keep working.

To rotate the signing key, follow this order, so Anthropic knows every key that signs an assertion:

1. Make a new key pair, and add the new public key to the issuer in the Anthropic Console beside the old one.
2. Store the new private key in its secret and restart the server.
3. Wait a few minutes, until every assertion signed with the old key has expired.
4. Remove the old public key from the issuer.

KMS rotates the key that encrypts people's logins once a year on its own, and keeps the old versions, so stored logins still decrypt.

### Tearing it down

Delete every bot workflow first, archived ones included, so komrad removes each task's worker, each orchestrator's worker and their volumes. Komrad makes workers and their volumes outside Terraform, so any left behind outlive the stack. Then run:

```sh
mise run infra:engine:destroy
```

Terraform can't destroy the database while deletion protection is on, so set `database_deletion_protection = false` in `terraform.tfvars` and apply before you destroy. RDS takes a final snapshot of the database, and the control plane's data volume gets one too. Snapshot names have to be unique, so a second teardown needs a new snapshot name. Terraform deletes dev boxes and their volumes with the rest.

Then remove the engine from Tailscale's admin console and delete its tailnet identity. The parameter sits outside Terraform, and its path is `/<name>/tailscale/state` for the stack's `name`:

```sh
aws ssm delete-parameter --name /komrad-development/tailscale/state
```

Finally, delete the issuer in the Anthropic Console and the bot's project in OpenAI.
