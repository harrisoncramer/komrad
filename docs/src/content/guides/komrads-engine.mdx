Komrad's own development runs on a remote engine in AWS. The engine triages issues and fixes bugs on GitHub automatically. The repository holds the infrastructure code, and this guide walks through it. [Running komrad remotely](../running-komrad-remotely/) explains the parts in general, and this guide shows how komrad builds each one.

## AWS resources

One EC2 instance runs the control plane: Tailscale, Caddy and the komrad server. It boots from a Packer image and keeps its config and state on a separate EBS volume. When Terraform replaces the instance, it moves the volume to the new one.

Postgres runs on RDS, in private subnets that only the control plane can reach. RDS manages the owner login's password, keeps it in Secrets Manager and keeps a week of automatic backups.

Secrets Manager also holds the GitHub App's private key, the OpenAI admin key, the key the control plane signs model assertions with, and the key the control plane uses to join the tailnet. A KMS key encrypts each person's GitHub login in the database. The control plane's IAM role can read those exact secrets and use that key.

Parameter Store holds the control plane's Tailscale identity. A full image replacement joins the tailnet as the same machine. Only the control plane's role can read or write it.

Every box is its own EC2 instance with its own encrypted EBS volume. Workers and dev boxes sit in a subnet in each of several availability zones. The control plane launches, starts, stops and terminates workers through EC2. Terraform makes dev boxes.

## The control plane

Everything on the control plane that has to outlive the instance sits on its data volume or in the database, so Terraform can replace it at any time. Agents run on boxes and keep running while the control plane is replaced. Their runners reconnect once the new control plane is up.

### The control plane image

Packer builds two images from the template in [`packer`](https://github.com/harrisoncramer/komrad/tree/main/packer). The control plane image starts from Ubuntu and installs Tailscale, Caddy and komrad. Each layer is a short shell script.

The image carries a komrad binary so the server can start on first boot, before any deploy has run. Each deploy replaces that binary, which means the image only needs rebuilding when a boot step changes.

### The komrad account

The server runs as an unprivileged account named komrad and uses the instance's role directly. The role lets it read its secrets, use the KMS key, and manage workers and their volumes. Its EC2 permissions cover the instances and volumes tagged as this engine's boxes.

Deploys, restarts and access grants need root, and they reach the instance through AWS Systems Manager. [Operator and CI access](#operator-and-ci-access) covers that path.

### The data volume

The control plane's data volume holds komrad's config and hooks, its cache and log, and Caddy's state. Tailscale's identity stays off it. When Terraform replaces the instance, the volume moves to the new one.

### Boot

Terraform hands the instance a short user data script. The script records which volume and database belong to it. It writes the identity provider into the server's config and points Caddy at the public listener. User data holds the provider's client secret, which the engine hands to every laptop that signs in.

The script also writes the tailnet name into Caddy's config, starts Caddy and joins the tailnet. Tailscale keeps its identity in Parameter Store, so a replacement instance comes back as the same device and asks for a new certificate. The tailnet unit fetches a key from Secrets Manager for the first join.

Systemd starts everything else in order. The data volume mounts first, and every unit that uses it waits for the mount.

Once the volume is up, the credentials unit reads the database owner's password from Secrets Manager, runs the migrations and writes the server's connection string. The server starts after it finishes and reads its keys from Secrets Manager. Caddy waits for Tailscale, which hands it the certificate, and for the volume, where it keeps its state.

An hourly timer reruns the credentials unit, so the instance picks up the owner's new password after RDS rotates it.

### Server restarts

A restart or a deploy restarts the server. Every runner keeps its agents running and reconnects once the new server is up. Each lease counts from the server's start, so every worker keeps its lease through a restart.

## Boxes

### The box image

The second image is the box image. It carries the runner, git, tmux, Docker, mise and the agent CLIs. Projects bring their own languages, such as Go and Node, through their workflow's setup command. Workers and dev boxes boot from the same image.

The image is rebuilt when an agent CLI or a system package changes. A deploy to the control plane updates every runner over its stream, as [the runner](../running-komrad-remotely/#the-runner) describes.

### Accounts on a box

The runner runs as an account of its own, which alone reads the runner's credential, its key and its files. The person and their agents share a second account. Docker runs rootless under that second account, so agents build and run containers there.

The box's firewall lets only the runner's account reach the control plane's private address. The instance metadata service answers root alone. The box's role carries what Systems Manager needs.

### Joining

A worker's user data carries a one-time join token. The runner trades it at boot for a box credential and keeps that credential where only its own account can read it. A dev box keeps its credential on its data volume, so it reads user data only the first time it boots.

### Placing workers

The control plane places each new worker in the zone with the most room. A worker's volume stays in that zone, so restoring an archived or lost task puts the new worker in the same zone. The engine's worker cap keeps launches under the account's EC2 vCPU quota.

### Dev boxes

An operator adds each person's dev box to Terraform, naming the person's sign-in issuer and subject and the box's size. Terraform makes the instance and its data volume, and replaces the instance and keeps the volume when the box image changes. The person starts and stops the box from the panel, and the control plane stops and starts the instance.

### Egress

Each box sits in a public subnet and gets a public address that changes each time it starts. Its security group allows outbound connections, which the box uses to reach the model providers and package registries. Forge traffic leaves from the control plane, so a forge that allowlists addresses needs only the control plane's Elastic IP.

## The database

Postgres holds every record an engine keeps, including the list of people who may use it. Komrad connects with three different logins, and each one can do only what its job needs. Only the control plane reaches the database.

### Database logins

The owner login owns the schema. <Command path="migrate" />, <Command path="engine ensure" /> and the grant commands connect as the owner.

The server runs as the engine login, which <Command path="engine ensure" /> creates for each engine. Postgres row-level security limits that login to its own engine's rows, so several engines can share one database without seeing each other's data.

The reader login reads the same rows as the engine login. When an agent queries the database through komrad's MCP tools, the query runs as the reader on the control plane.

### Database credentials

RDS creates the owner login and stores its password in Secrets Manager. The control plane reads the secret each time it needs the owner, and keeps the password in memory.

The credentials unit runs at boot, during every deploy and once an hour. Each run migrates the database, makes sure the engine login exists, and writes the server's connection string to a file only root can read. Because the unit runs during deploys, new migrations land before the new server starts. The hourly run picks up the owner's new password after RDS rotates it.

### Backups

RDS keeps automatic backups for seven days. Deletion protection is on, and Terraform refuses to destroy the database until you turn it off, as [tearing it down](../standing-up-an-engine/#tearing-it-down) shows.

## Access

A remote engine lets in only people it can identify and whom an operator has granted access. People prove who they are by signing in with an identity provider, and the engine looks up a grant for each of them. Komrad's engine sits on a Tailscale network, so a laptop has to be on that network to reach it. Operators reach the control plane and every box through AWS Systems Manager, which opens shells over the instance's own outbound connection.

### Signing in

Each person signs in once per engine, from their laptop:

```sh
komrad login --engine remote
```

Komrad asks the engine's `/sign-in` page which identity provider it trusts and opens a browser at that provider. The person signs in there, along with any MFA the provider requires. The provider then sends the browser back to komrad on `127.0.0.1:8085` with a one-time code, and komrad trades the code for an ID token and a refresh token. Komrad checks that the answer belongs to the sign-in it started. Only the provider ever sees the person's password.

The panel can sign a person in too. On an engine at a URL, the panel asks the engine whether the person has access before it shows anything. Without a sign-in it shows only a sign-in screen, and enter opens the provider's page in the browser. If nobody granted the person access, the panel says to ask an operator. If the engine or the provider doesn't answer, the panel says so, and enter tries again.

Komrad keeps both tokens in the system keychain. A laptop with no keychain keeps them in a private file under komrad's state directory. <Command path="logout" /> removes them from both places. If a panel for that engine is open on the same laptop, logout closes any agent terminal it was showing and restarts it at the sign-in screen. A terminal you started yourself keeps its stream until the token it holds runs out, at most an hour later. A terminal opened while the laptop has no sign-in says so and attaches once you run <Command path="login" />.

### Tokens

The panel and every command send the ID token with every request. The token lasts about an hour at most providers. When it has less than five minutes left, komrad uses the refresh token to get a new one without opening the browser. If the provider refuses, komrad asks the person to sign in again. If the provider doesn't answer, komrad says so, and the same sign-in works once the provider is back. <Command path="token" /> prints a current ID token, so a script can call the engine's API with it.

A terminal or the panel's stream of events can stay open for hours. While a request is open, the engine checks the grant again every minute, and it ends the request when the token expires. An open terminal sends a fresh token down the stream before the old one expires, so the terminal stays open. It also sends a message every 20 seconds, so a proxy in front of the engine never sees a quiet terminal as a dead one. The panel reopens its stream with a fresh token. When the stream ends because the grant was revoked, the sign-in can't be renewed, or the provider doesn't answer, the panel clears everything it showed and goes back to its sign-in screen. If only the engine stopped answering, the panel keeps what it showed and reconnects.

### Request checks

The public listener checks every request. The token has to carry a valid signature from the provider the engine trusts, it has to have been issued for komrad, and it can't have expired. A request that fails any of those checks gets a 401.

Next the listener looks for that person's grant on this engine, and answers 403 if there isn't one. Once a request passes, the person's identity goes with it into the handler and into the log.

### Access grants

<Command path="engine grant" /> gives a person access by email address, and <Command path="engine revoke" /> takes it
away. An email address can move to a different account, so the first time a granted person signs in with a verified
email, the engine records the permanent id their provider uses for that account and matches on that id afterwards.

A grant lets a person use their own workflows and the bot's, as [workflow owners](../running-komrad-remotely/#workflow-owners) describes. They can open a shell on their own dev box and on any bot task's worker. Anyone in a shell on a worker can reach that task's repositories as the bot, so grant access only to someone you would trust with the bot.

Revoking a grant also deletes the person's stored GitHub login. The engine caches each grant for a minute, so a revoke takes effect within a minute, open terminal sessions included. If the engine can't reach the database to check a grant, it refuses the request.

Both commands connect as the database owner, which on komrad's engine means running them as root on the control plane. [Granting and revoking access](../standing-up-an-engine/#granting-and-revoking-access) has the commands.

### Provider registration

An operator registers komrad with their identity provider once, as a desktop app with `http://127.0.0.1:8085` as its redirect address. The provider issues a client id. On komrad's engine, `sign_in_issuer` and `sign_in_client_id` in `terraform.tfvars` name the provider and that id, and Terraform writes them into the engine's config when it builds the control plane. Changing either one replaces the control plane, the same as a new image does. An engine you run yourself takes them in the <Setting path="sign_in" label="[sign_in]" /> table of its config.

Google also issues a client secret. The secret can't stay secret, since the engine hands it to every laptop that signs in, but Google requires one, so it goes in `sign_in_client_secret` as well. Publish the app on Google, or make it internal to your Workspace. If you leave it in testing mode, Google makes everyone sign in again every week.

### Server listeners

The server listens on two loopback addresses and on the control plane's private address.

The public listener, on loopback, takes people's requests from Caddy and runs the checks above on each one. It serves the API, plus one public page that tells a panel which identity provider to use.

The loopback listener serves the CLI in a shell on the control plane. It skips the identity checks, because only processes on the control plane can reach it.

The runner listener, on the private address, takes each runner's stream. It accepts only a box's credential, and every agent's call to komrad arrives over it.

### Operator and CI access

Operators reach the control plane and every box through AWS Systems Manager, which reaches each instance over its own outbound connection. A session opens a shell as a user with sudo. Deploys and restarts also go through Systems Manager, whether they start on a laptop or in GitHub Actions.

Anyone whose AWS credentials let them open a session or send a command to an instance has root on it. Guard those credentials the way you would guard root.

## Network

Komrad's engine opens no TCP ports to the internet. People reach the control plane over a tailnet, a private network Tailscale builds between devices an operator lets in. A person needs a device on the tailnet and a grant on the engine. Boxes stay off the tailnet.

The engine's address is its tailnet name, such as `https://komrad.tail1234.ts.net`. The name resolves only through Tailscale's DNS, so the laptop needs Tailscale running with DNS on. Caddy gets the certificate for that name from Tailscale. The name appears in public certificate logs, but nothing on the internet can reach it.

The control plane has an Elastic IP. The security group allows Tailscale's UDP port 41641 on it, so laptops connect directly instead of through Tailscale's relays. Setting `tailscale_direct_connections = false` closes it.

### The tailnet policy

The control plane joins your tailnet as one device tagged `tag:komrad-engine`, and the rest of your policy stays as it is. Tailscale issues an auth key for a tag only once the policy names an owner for it, so add the tag to `tagOwners` before you create the engine's key:

```json
"tagOwners": {
  "tag:komrad-engine": ["autogroup:admin"]
}
```

People reach the engine on 443. Tailscale's default policy lets every member reach every device, so a tailnet still on it needs nothing more. A tailnet with its own rules needs a grant naming whoever should reach the engine:

```json
"grants": [
  {
    "src": ["autogroup:member"],
    "dst": ["tag:komrad-engine"],
    "ip": ["tcp:443"]
  }
]
```

### Firewalls

On the Tailscale interface the control plane's firewall accepts new connections to 443 only.

The control plane's security group accepts runner streams from the boxes' security group. The database's security group accepts only the control plane. Each box's own firewall lets only the runner's account reach the control plane.

### Outside users

Someone outside your tailnet needs the engine shared with them from Tailscale's admin console, plus a grant. Remove both when they leave.
