## Merges to main

When CI passes on main, `main-release.yml` publishes the binaries as a prerelease tagged `tip`. Each merge replaces it, so its download address stays the same. If the merge changed the docs, `docs-deploy.yml` publishes them as `latest`. The engine keeps running its current release.

## Releases

`mise run release:cut` tags the current commit with a version, such as `v0.4.0`, and pushes the tag. A person has to run it, because a tag pushed by CI doesn't start other workflows. Komrad doesn't keep backward compatibility, so releases stay on `v0.x` and each release bumps the minor version.

The tag starts `release.yml`. It runs the full checks against the tagged commit, publishes a GitHub release with a changelog, publishes the docs for that version, and deploys the release to the engine. A tag push starts the workflow only once. If the workflow fails, rerun it on the same tag with `gh workflow run release.yml --ref v0.4.0` instead of moving the tag.

## Deploys

`mise run remote:deploy` deploys the checkout's build to the engine. The release workflow runs the same task through `engine.yml`.

The task builds komrad for the engine and uploads it to the Terraform state bucket. It then sends the instance a command through Systems Manager. The command downloads the binary, stops the server, runs the credentials unit, and starts the server. The credentials unit migrates the database, so new migrations apply before the new server starts. [The database](../engine-database/#credentials-on-our-engine) covers the credentials unit.

Agents keep running through a deploy, because stopping the server doesn't stop tmux. [The machine](../engine-machine/#agents-during-server-restarts) explains why.

A deploy skips when the engine is stopped, because Systems Manager can't reach a stopped instance. The next deploy after the engine starts includes the same changes.

A panel connects only to an engine built from the same commit. A deploy stamps the binary with its commit. A deploy from a checkout with uncommitted changes stamps a `-dirty` version instead, and also builds a matching panel at `dist/komrad-panel`.

To deploy any branch or tag, dispatch `engine.yml` from the Actions tab and choose the ref. It runs the full checks first and needs no AWS credentials on your laptop. [Runbooks](../runbooks/#deploying-or-rolling-back) uses it for rollbacks.

## Image updates

The image changes when a tool, a boot step or a system package needs updating. Dispatching `image.yml` builds an image and records its id in Systems Manager's parameter store. It doesn't apply the image.

Applying an image replaces the instance, which stops every running agent. `mise run remote:reimage` reads the recorded image id, lists the agents that will stop, and asks before continuing. It then sets the image in your `terraform.tfvars` and applies. The data volume moves to the new instance and the database doesn't change, so the agents can be resumed.

The image's komrad binary is the version that was current when the image was built. Deploy after reimaging if the engine should run a newer one.
