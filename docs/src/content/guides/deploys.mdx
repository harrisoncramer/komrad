Merging and shipping are two different things here. Merging to main builds a fresh copy of komrad that anyone can try, but it doesn't promise anything and it doesn't touch the engine. Shipping happens when someone tags a release, and that's the only thing that reaches the engine on its own.

## A merge

Once CI passes on main, GitHub publishes the new binaries as a prerelease called `tip`. Every merge replaces it, so the download link never changes, and if the merge touched the docs, the site's `latest` version updates too. The engine keeps running whatever release it already had.

## A release

To cut a release, run `mise run release:cut` with the new version, such as `v0.4.0`. It tags the current commit and pushes the tag. A person has to do this, since a tag pushed by CI doesn't set off any other workflows. Komrad doesn't promise backward compatibility yet, so releases stay on `v0.x`, and a minor bump is the normal one.

The tag kicks off the release workflow. It runs the full checks against the tagged commit, publishes the binaries with a changelog, publishes the docs for that version, and deploys the release to the engine. If it fails partway through, run the workflow again on the same tag rather than moving the tag.

## A deploy

`mise run remote:deploy` puts whatever your checkout builds onto the engine, and the release workflow runs the same task. It builds komrad for the engine, uploads it to S3, and asks the machine through Systems Manager to install it. The machine then stops the server, migrates the database, and starts the new server. Migrating in between means a new migration always lands before the code that needs it.

Agents keep running the whole time, because stopping the server leaves tmux alone. [The machine](../engine-machine/#why-agents-survive-a-restart) explains how.

If the engine is switched off when a deploy runs, the deploy skips. Systems Manager can't reach a stopped machine, and the next deploy carries the same changes anyway.

A panel only talks to an engine built from the same commit, so a deploy stamps the binary with the commit it came from. If your checkout has uncommitted changes, there's no commit to stamp, so the deploy marks the build as dirty and also builds a matching panel at `dist/komrad-panel` for you to use with it.

To deploy any branch or tag without AWS credentials on your laptop, run the engine workflow from the Actions tab and pick the ref you want. That's handy when your laptop is the thing that's broken, and it's how [runbooks](../runbooks/#deploying-or-rolling-back) rolls back.

## A new image

The machine's image changes rarely, when we need a new tool, a change to how the machine boots, or a security update. Running the image workflow builds one and records its id, but it doesn't put it to use.

Putting a new image to use means replacing the machine, and every running agent stops when that happens. `mise run remote:reimage` takes care of it. It tells you which agents will stop and asks before it does anything, then points Terraform at the new image and applies. The data volume moves to the new machine and the database isn't touched, so you can resume the agents afterwards.

The new image carries whatever komrad was current when it was built, so deploy afterwards if the engine should run something newer.
