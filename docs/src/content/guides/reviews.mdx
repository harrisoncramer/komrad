## Local reviews

When making a change locally, it's often faster to iterate directly with an LLM rather than pushing the changes to a remote.

Komrad supports this with the concept of a _local review_.l

With local reviews, you can provide feedback to agents directly in your editor or terminal, rather than via a forge like Github or Gitlab. This helps keep feedback loops quick and reduce CI spend for agent-authored changes.

With local reviews, you can read the agent's diff, leave comments on its lines, and edit it yourself. The agent will respond in the same view.

<Alert variant="info">Local reviews are completely optional, you can use komrad without them.</Alert>

Komrad's local review model is quite similar to how <a href="https://www.gerritcodereview.com/">Gerrit</a> does code review, where you can step through chunks of changes (known in komrad as chapters) that correspond to review rounds. Each chapter is tied to a specific diff in the code that an agent has made.

### Opening a review

Put the cursor on an agent, press <Key name="menu.open" /> to open its [menu](../navigation/#the-agent-menu), and pick review with <Key name="menu.review" />. The main panel then shows everything the agent changed since its branch left the base.

The sidebar holds a tree of the files the change touches, and the main view holds the diff and conversation.

### Leaving comments

Press <Key name="review.compose" /> on a line to comment on it.

The draft is not submitted to the agent until you submit your review, like in Github or Gitlab. While you hold the drafts, the diff is "frozen", so the lines you are commenting on do not move.

### Editing the code yourself

Sometimes fixing a line is quicker than describing the fix. Press <Key name="review.edit_file" /> to open the file in your editor (the `$EDITOR` value in your terminal, like vim) beside the diff. Komrad pauses the agent while you edit, since you are both working in its checkout. When you close the editor the agent carries on from your change.

### Sending

When you are done reading, press <Key name="review.send" /> to send the review. Komrad asks if you have anything to say about the work as a whole, then sends it. Sending stops the agent mid-turn, so it reads your comments now rather than when it finishes what it is doing.

Under the hood, each of your comments is sent with the lines it was written on and the code around them, so the agent can find the spot even after the file has moved.

The agent answers in your threads, and can settle them. To see exactly what the agent changed in response to your suggestion, press the <Key name="review.answer" /> key. This will show the specific change the agent made. You can settle or reopen any comment yourself.

### Stepping through history

Each review you send closes a "chapter" in komrad, which holds the work you had read when you sent it. Stepping through chapters shows each review, with the comments written on it and the code that changed as a result.

Past chapters take replies but not new comments, since their lines may no longer exist in the agent's work.

### Agent Reviews

Recall from the agent guide that implementer agents can spawn reviewer agents to review their work.

Under the hood, reviewer agents use the same process as you do, by leaving comments on the changes from an implementer.

These comments are hidden by default, press TODO to show them.

## Remote Reviews (Github and Gitlab)

Once you're happy with the work locally, the next step is to push it to a forge, like GitHub or GitLab.

<Alert variant="info">
  Connect a forge before agents can push or komrad can follow their pull requests. [Connecting a
  forge](../install/#connecting-a-forge) covers GitHub and GitLab.
</Alert>

### What komrad reads

While an agent is live, komrad watches the pull requests in its repository. It notices when one is opened from the agent's branch, when checks pass or fail, when it is approved, and when it is merged. That shows up as a symbol on the agent's row. Some of those changes also [tell the agent](../events-and-messages/#what-komrad-tells-an-agent), such as checks failing or the branch conflicting with its base.

Komrad reads the pull requests opened from each live agent's branch. A repository where something is likely to change soon, such as checks still running, a branch that just moved, or a pull request komrad just wrote to, is read every five seconds. Every other repository is read once a minute. When the forge says little of the hour's budget is left, every repository on that host drops to once a minute until the budget comes back.

Komrad also reads the review comments on each open pull request or merge request a live agent is linked to, drafts included, once a minute. They are copied into the agent's review as threads of their own and counted with yours on its row. Komrad holds a comment from someone who cannot push to the repository until you send your review, and never writes anything back to the forge.

### Comments from the forge

When the agent's pull request or merge request has review comments, komrad copies them into the review as threads of their own, each under its author and line. Press <Key name="review.jump" /> to move to the next thread and read it out. A reply or an edit on the forge lands in the same thread, and resolving one there resolves it here.

Comments from someone who can push to the repository reach the agent on their own. Comments from anyone else are held until you send your review, or until you reply in their thread, so nothing from a stranger reaches the agent without you seeing it first.

The agent answers forge comments in the review, never on the forge itself.

### Where the token lives

The database holds only which forge and which account. The token itself sits in a file only your user can read, and never shows up in logs. This is the same arrangement as the GitHub CLI or your SSH keys.

### How agents push

Agents never hold a credential of their own, and no token is ever typed into a pane, so none can leak into a transcript. Komrad hands each tool the credential when it runs.

Komrad puts its own `gh` and `glab` ahead of every agent's PATH. Each one asks komrad for a credential and then runs the real tool. If the agent's environment already sets a token the tool reads, such as `GH_TOKEN` or `GITLAB_TOKEN`, komrad leaves the tool alone.

For GitHub, `gh` gets a token from the App when <Setting path="github_app" label="[github_app]" /> is set. Otherwise it uses the login `gh` already has on the machine. Git reaches GitHub through <Command path="github credential" />, which the engine sets up for you. On your laptop, git uses whatever credential you already have.

For GitLab, `glab` gets the token of the connection for the checkout's host, in a config that names that host alone, so the token is never sent anywhere else. With no connection for that host, it uses the login `glab` already has. Git reaches GitLab through <Command path="gitlab credential" /> once you add a line for each host.

```sh
git config --global credential.https://gitlab.example.com.helper '!komrad gitlab credential'
```
