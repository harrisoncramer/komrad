Komrad is one binary. The binary is used to run the client, or the server, known as the _engine_.

The client for Komrad runs on your machine. It renders the view of komrad's state in your terminal, and wraps around existing CLI tools like Claude or Codex.

The server, known as the engine, runs your agents and records their activity into Postgres, so you can search through chat history, spawn multiple at once, or have them communicate. The engine can run on your machine or on a remote box. You can also connect to different engines from one machine.

## Install the binary

```sh
gh release download tip --repo harrisoncramer/komrad --pattern komrad-darwin-arm64 --output ~/.local/bin/komrad
chmod +x ~/.local/bin/komrad
```

Swap `darwin-arm64` for your platform.

The `tip` binary is rebuilt from main on every merge and is unstable. Stable releases have a version number and a changelog. Every release carries a `checksums.txt` file.

## Automatic installation

Run <Command path="setup" /> once the binary is on your PATH. It walks through the machine one step at a time.

## Manual installation

### Create your database

Komrad requires Postgres. For local development, running Postgres via Docker is the recommended approach.

```sh
docker run --name komrad \
	-e POSTGRES_USER=komrad_owner \
	-e POSTGRES_PASSWORD=password123 \
	-e POSTGRES_DB=komrad \
	-p 5432:5432 \
	-v komrad_data:/var/lib/postgresql \
	-d postgres:18
```

Postgres takes a few seconds to start. Wait until `docker exec komrad pg_isready -h localhost` reports that it is accepting connections before moving on.

The database requires one admin-like user. The komrad engine uses this user to automatically run migrations on start, and each time you update your binary.

```sh
export KOMRAD_OWNER_DATABASE_URL=postgres://komrad_owner:password123@localhost:5432/komrad
komrad migrate
komrad engine ensure laptop
```

The <Command path="migrate" /> command is the only command that changes the schema.

  Run <Command path="doctor" /> to check for configuration or installation issues.
</Alert>

Provide your database connection string to the <Command path="migrate" /> command, and create your first engine. The engine is named `laptop` here.

The komrad engine is one running komrad on one machine. Several can share one database, which enables multiple developers to share the same Postgres database, or for a single developer to scale their workload horizontally across machines.

Komrad will safely auto-migrate the database after you first set it up.

### Write the config

Komrad's configuration is stored in a TOML file.

The <Command path="engine ensure" /> command prints an initial <Setting path="connection" label="[connection]" /> block that can be added to the database with a login for the engine. Run it, then put the engine block in `~/.config/komrad/config.toml`, and add the owner URL from the previous step beside it.

```toml
[connection]
owner_database_url = "postgres://komrad_owner:password123@localhost:5432/komrad"
database_url = "postgres://komrad_engine_laptop:8f3a1c9e2b7d4e6f@localhost:5432/komrad"
```

The <Setting path="connection.owner_database_url" label="owner_database_url" /> is only used by <Command path="migrate" /> and <Command path="engine ensure" />. The service itself connects with <Setting path="connection.database_url" label="database_url" />.

### Open the panel

Komrad runs every agent in a tmux server of its own, so tmux must be installed. Using tmux yourself is optional.

Run <Command path="open" /> to open the panel. The first open starts the service in the background.

## Komrad + Tmux

The panel takes over the terminal you open it in, and a tmux pane works like any other. <Command path="attach" /> shows the same panel in a second terminal. Closing the panel with `ctrl+c` only detaches it, so the service and your agents keep running.

If your own tmux prefix is `ctrl+space`, give your tmux a different one, since the panel keeps its own keys behind it.

## Connecting a forge

In order for Komrad to push or pull data from your forge (like Github or Gitlab) you have to connect it.

Komrad connects a forge once with <Command path="forge connect" /> command.


### GitHub

On your laptop, the simplest way is to hand komrad the token the GitHub CLI already holds.

```sh
gh auth token | komrad forge connect github.com
```

Any personal access token works the same way, as long as it can read the pull requests of your repositories. For GitHub Enterprise, add `--kind github` and, if needed, `--api-url`.

If you're connecting a GitHub App, set it up in <Setting path="github_app" label="[github_app]" />, and connect it with `--method github-app` setting. Komrad makes a token from the App, which expires after an hour, and makes a new one whenever it needs to. [Administering the engine](../engine-admin/) covers registering the App.

```sh
komrad forge connect github.com --method github-app --engine remote
```

### GitLab

GitLab takes a personal access token with the `api` scope.

```sh
komrad forge connect gitlab.com --token-file ~/.config/gitlab-token
komrad forge connect gitlab.example.com --kind gitlab --token-file ~/.config/gitlab-token
```

GitLab has no App to make short-lived tokens from. On a machine other people can reach, such as the remote engine, connect with `--method rotating-token` so the token komrad holds does not live forever. Komrad swaps the token for a new one as soon as you connect, so the one you pasted stops working at once.

Use the <Command path="forge disconnect" /> to revoke the current token with GitLab before forgetting it.

```sh
komrad forge connect gitlab.com --method rotating-token --token-file ~/.config/gitlab-token --engine remote
```

If a rotation is ever refused, the connection shows as refused in <Command path="forge list" />. Connect it again with a fresh token.

### Self-Hosting

A self-hosted forge needs two more things.

Komrad cannot tell which forge a host runs from its name, so pass `--kind github` or `--kind gitlab`. If its API is somewhere other than `https://<host>/api/v3` for GitHub or `https://<host>/api/v4` for GitLab, pass `--api-url` as well.

Some hosts take SSH paths like `ssh.gitlab.example.com`. List each pair in <Setting path="git.ssh_hosts" label="ssh_hosts" /> so a remote on the SSH name finds the connection for the web host. Public names such as `ssh.github.com` and `altssh.gitlab.com` are already known.

## Upgrading

Download the new binary over the old one, then stop the service and migrate.

```sh
komrad stop
komrad migrate
```

A running service keeps its old build until it is stopped, so the stop is what swaps it. Open the panel again and it starts the new build. Agents keep running throughout, because they live in tmux, not in the service.

The panel is open and empty. The first thing it needs is a [workflow](../workflows/).
