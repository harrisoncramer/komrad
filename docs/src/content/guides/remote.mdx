[Agents](../agents/) on your laptop stop when your laptop sleeps. Komrad can run them on a remote machine instead. The panel stays on your laptop and looks the same. What moves is the engine: the service, the database, and every agent's terminal.

Komrad's own repository works this way. [Administering the engine](../engine-admin/) covers building that machine. This guide covers using one that exists.

## Telling your panel about an engine

An engine is a small config file on your laptop in `~/.config/komrad/engines/`, named after the engine. It sets the <Setting path="connection" label="[connection]" /> table: <Setting path="connection.forward" label="forward" /> says how to carry the engine's API back to your laptop, and everything the panel does on the engine goes through that API. For a host your SSH config already knows, a plain <Setting path="connection.ssh" label="ssh" /> destination is enough.

Keep the engine's SSH host keys in a file of their own. A rebuilt engine answers on the same address with a new key.

## Choosing where to open the panel

<Command path="open" /> opens your laptop's panel. <Command path="open" args="--engine remote" /> opens the engine named
`remote`, and `--engine local` names your laptop.

Every panel shows which engine it is on at the top right, with the release its server runs, or its commit when it runs no release. The dot beside it is green while the engine's heartbeat arrives, red once it stops, and yellow while the engine runs a different build from yours. The message it flashes beside the engine says why, and <Key name="messages.open" /> opens it whole with what to do.

To move to another engine, close the panel and run <Command path="open" args="--engine" /> with that engine's name.

## Attaching to an agent

An agent's terminal on the engine is streamed to your panel, and <Command path="terminal" args="AGENT" /> does the same in any terminal. The agent's window takes the size of the terminal attached to it, so it fills the stage and follows it when you resize.

The terminal in an agent's [subpages](../navigation/#subpages) works the same way. It opens a shell on the engine, in the agent's directory there, and streams it to the pane below the stage.

The exception is a window someone fixed at a size on the engine itself, for example by opening a panel there, which runs tmux's `resize-window` and sets the window's `window-size` to `manual`. That window keeps its size wherever it is attached, so a smaller terminal crops it and a larger one leaves blank space around it.

## Signing the agent CLI in

Agents on the engine run a CLI that has to be logged in. Do that once on the engine: start the CLI and log in. The login lives on the engine's data disk.

Each agent also works in a fresh worktree, and the CLI asks whether to trust every directory it has not seen. Turn on <Setting path="harness.claude.trust_launch_dirs" label="trust_launch_dirs" /> for each CLI the engine runs, so komrad answers that question before the agent starts. Without it, every new agent sits waiting at that question.

## Keeping the two builds in step

Your komrad and the engine's have to be the same build. The engine moves when a release is published, so when the two disagree it is usually your laptop that moved on. Install the release the engine runs. <Command path="doctor" /> checks both and says what to do.

## When the engine is off

An engine costs money every hour, so it may be switched off when nobody is using it. Switching off keeps the disk, the database and the address. Every agent stops, and you resume the ones you want once it is back.

Using an engine is one thing. [Administering the engine](../engine-admin/) is building one.
