People reach an engine at an HTTPS address and prove who they are with a token from an identity provider. The engine checks that token on every request, then checks that its owner let that person in. Nobody who uses the engine needs a shell on its machine.

## Two listeners

The server listens on two loopback addresses, and neither is reachable from the network on its own.

The loopback listener, at `127.0.0.1:8787`, is for things already on the machine: the agents, their MCP tools, and the CLI in a shell there. It trusts whoever calls, because reaching it at all means being on the machine.

The public listener is for people. Caddy passes requests to it, and it checks every one, including any that come from the machine itself. It serves the API, plus one public page that tells a panel which identity provider to sign in with. The MCP endpoint and the server's stop and health routes stay off it. It also ignores the headers that name an agent, so a person can never pass as one.

## Signing in

Each person signs in once per engine, from their laptop:

```sh
komrad login --engine remote
```

Komrad asks the engine which provider it trusts, and opens a browser there. The person signs in at the provider, with whatever MFA it asks for, and the browser comes back to komrad on `127.0.0.1:8085` with a one-time code. Komrad trades the code for two tokens. The ID token lasts about an hour and goes with every request. The refresh token gets a new ID token without opening the browser again. Both live in the system keychain, or in a file only that person can read where there is no keychain.

The panel refreshes the ID token before it runs out, including on an open terminal, so a session never drops for a stale token. Once the refresh token stops working, the panel says to sign in again.

## What the engine checks

For each request, the public listener checks that:

1. The provider signed the token, against the keys it publishes.
2. The token came from the provider this engine trusts.
3. The provider issued it for komrad's id there.
4. It hasn't expired.

A request that fails any of those gets a 401. Then the engine checks that the person holds a grant on this engine, and a request without one gets a 403.

Everything that passes carries who sent it, by name and by provider id, into the code that handles it and into the log.

## Who may use an engine

<Command path="engine grant" /> lets a person in by their email, and <Command path="engine revoke" /> turns them away.
The first time a granted person signs in with a verified email, the engine records the permanent id their provider gives
that account. From then on it matches on that id alone.

Access is all or nothing. Anyone granted access can do everything the panel does, including opening a shell on the engine's machine as the account agents run as. Grant it only to people you would give that machine.

The engine caches each person's grant for a minute, so revoking takes effect within a minute, even on an open terminal. Disabling someone at the provider stops their refreshes, so they're out within the hour either way. If the database can't be reached, the engine refuses everyone.

Both commands connect as the database owner, so on our engine they run as root. The image wraps them as `komrad-access`, which [runbooks](../runbooks/#granting-and-revoking-access) shows.

## Registering komrad with the provider

The owner registers komrad once with their provider, as a desktop app, with `http://127.0.0.1:8085` as its return address. The provider hands back a client id, and the engine's config names the provider and that id. Google also hands back a client secret, which protects nothing, since every copy of komrad carries it. It goes in the config beside the id.

With Google, publish the app, or make it internal to your Workspace. An app left in testing makes everyone sign in again every week.

## The network

Port 443 is open to the internet. The token is the lock, as for any service you sign in to. An owner with fixed office or VPN addresses can limit 443 to those.

Port 80 is open too, because that's how Let's Encrypt confirms Caddy holds the domain. Caddy answers nothing there except that check and a redirect to HTTPS.

No other port is open. Our engine has no SSH. An engine file can still name an <Setting path="connection.ssh" label="ssh" /> or <Setting path="connection.forward" label="forward" /> tunnel in place of a <Setting path="connection.url" label="url" />, but that reaches the loopback listener and skips sign-in, so we don't use it.

## Operators and CI

Whoever runs the machine reaches it through AWS Systems Manager, which needs no open port and no key on the machine. A session opens a shell as a user with sudo, and `sudo -u komrad -i` from there gives the account agents run as.

Deploys, restarts and image changes send commands the same way, from a laptop or from GitHub Actions. [Runbooks](../runbooks/) has the commands.

Anyone whose AWS credentials can open a session on the instance or send it a command has root on it. Treat those credentials as the machine's real keys.
