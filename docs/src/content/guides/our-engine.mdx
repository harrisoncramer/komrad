Komrad's own development runs on one remote engine on AWS. This guide shows how its pieces map onto [the ones every engine needs](../running-komrad/). The Terraform in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine) and the Packer template in [`packer`](https://github.com/harrisoncramer/komrad/tree/main/packer) build exactly this. You can copy it, but you don't need AWS to run an engine.

One EC2 instance runs the server and every agent. It is an arm64 Graviton machine, a `t4g.xlarge` by default, booted from an image Packer builds. An Elastic IP gives it an address that outlives the instance. The engine's domain points at that address, so it survives a rebuild too.

A separate encrypted EBS volume holds the komrad account's home, the worktrees and the build caches. It follows the instance when the instance is replaced.

RDS Postgres sits in private subnets, and only the instance's security group can reach it. RDS manages the owner password and keeps it in Secrets Manager. Backups are kept for seven days.

Secrets Manager also holds the GitHub App's private key under `komrad/github-app`. The instance's role can read only that prefix and the database's own secret.

The security group opens ports 443 and 80 and nothing else. Caddy answers on both, with a certificate for the engine's domain from Let's Encrypt. There is no SSH. Operators reach the machine through Systems Manager, as GitHub Actions does.

## How CI reaches it

GitHub Actions never holds an AWS key. Each run asks GitHub for a signed token, and AWS trades it for credentials on the `komrad-development-ci` role. The role trusts only this repository's branches and its version tags, so a fork's pull request cannot use it.

That role can read Terraform's state, stage a binary in the state bucket, send the instance a command through Systems Manager, stop and start the instance, and build an image. It cannot log in.

## Terraform state

Both Terraform stacks, the engine and [the docs site](../docs-site/), keep their state in one S3 bucket under different keys. Nobody runs `terraform` directly. Each stack has a mise task group, such as `mise run infra:engine:plan`, that points Terraform at the right directory and backend.

The backend and the variables name an account's own bucket, addresses and keys, so neither file is in the repository. Each has an example beside it to copy.

## Cost

The instance is most of the bill, and it bills by the hour. A GitHub Actions schedule stops it at 10pm and starts it at 7am, New York time, an hour earlier in winter. The volume, the database and the Elastic IP still bill while it is stopped. [Runbooks](../runbooks/#stopping-and-starting) covers stopping it by hand.
