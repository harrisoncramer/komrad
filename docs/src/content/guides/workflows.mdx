Everything you do in komrad happens inside a _workflow_. A workflow is a bucket of settings: the directory work starts from, the harness its agents run, like Claude or Codex, the flags they launch with, and whether each task gets a worktree of its own.

<Alert variant="warning">This guide assumes you have [installed komrad](../install/) already.</Alert>

Think of a workflow as a shared blueprint for one kind of work in one repository. You might keep one for bug fixes and another for feature work in the same repository, each with its own flags and context.

## Creating your first workflow

Clone a real repository to work in. This guide uses Neovim.

```sh
git clone https://github.com/neovim/neovim ~/neovim
cd ~/neovim
```

Run <Command path="open" />, open the menu with <Key name="menu.open" /> and press <Key name="menu.new_workflow" />. Name the workflow `neovim`. Its directory defaults to the one you opened komrad in, and its provisioner decides whether each task gets a worktree. Press enter to create it.

## The orchestrator

Creating a workflow also starts its _orchestrator_, an agent that belongs to the workflow itself. It is folded into the workflow's row in the list, and pressing enter on the workflow opens it.

The orchestrator writes no code of its own. You tell it what you want done, and it creates [tasks](../tasks/) for the work and puts agents on them. It passes messages between those agents and gathers what they find. Think of it as a lead who splits the work up and keeps track of it.

You don't have to go through the orchestrator. You can start a task yourself, which the [next guide](../tasks/) shows.

## Shared context

A workflow can carry _shared context_, which every agent it starts reads. This is where you put what you would otherwise tell each agent by hand: how tests run, how commits are written, and so forth.

In the Neovim example, that might be "Run make lint before committing any Lua change."

The workflow's context comes after your <Setting path="context">global context</Setting>, which every agent reads whatever workflow it is in. In the video below the global context says only that Neovim is the best editor, and the agent has read both.

## Worktrees

Komrad has first-class support for [git worktrees](https://git-scm.com/docs/git-worktree). Set the workflow's provisioner to worktree and each new task gets a worktree of its own, cut from the workflow's base branch. Every agent on that task works inside it, isolated from every other task. The worktree is removed when the task is deleted.

Komrad puts worktrees in <Setting path="worktrees.dir" /> unless the workflow names a directory of its own. The worktree section of the workflow's settings also lists files to copy or link into each new worktree, such as a `.env` file git does not track.

When you start a task you can still choose to run it in the workflow's directory instead. That suits work that only reads, such as answering a question about the code.

<Alert variant="info">
  A task without a worktree works directly in the workflow's directory, alongside every other task that does the same.
</Alert>

## Changing a workflow

Hover the workflow, open the menu with <Key name="menu.open" /> and pick edit with <Key name="menu.edit_row" />. The settings are the same as when you created it, plus the [hooks](../hooks/) and the prompts komrad sends agents when something happens.

## Archiving and restoring

Archiving a workflow puts it in cold storage. Open its menu with <Key name="menu.open" /> and press <Key name="menu.archive" />. Its orchestrator and every live agent in it are archived, and with them its tasks. Nothing is deleted. The workflow moves to the archive, where you can restore it, or delete it for good later.
