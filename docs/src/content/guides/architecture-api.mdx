Every endpoint in komrad starts as one RPC in a protobuf file. Komrad generates the handler's interface from that declaration, and builds the CLI command, the MCP tool and the reference page from it too.

Each RPC carries a `surfaces` annotation. It says whether the RPC gets a CLI command and an MCP tool, what each one is called, and which agent roles may use it. An RPC that leaves a surface off has to give a reason. `RecordReport`, for example, isn't an MCP tool, because only komrad's own hook binary may call it.

## Lint

Buf lint runs with a plugin of komrad's own, which checks what each method and field declares. A method named `List` must declare no side effects, a method named `Archive` must be idempotent, and an id field must refuse an empty value. The plugin also requires a complete `surfaces` annotation on every method, so a method can't reach the CLI and miss MCP without the file failing lint.

## Generation

Buf generate runs three generators: the standard protobuf one, the Connect one, and komrad's own. Komrad's generator writes a strict interface whose methods return a typed failure in place of an `error`, and an adapter that turns that failure into a Connect code. Handlers implement the strict interface, so each handler body is a single call and the mapping from failures to codes lives in one place.

## The server

A request passes through a few interceptors on its way to a handler. A guard refuses any Host header that isn't loopback, which stops a web page in your browser from reaching the API. A recovery layer turns a panic into an error. The JSON codec refuses unknown fields where the default codec would quietly drop them. Validation then runs the rules declared in the proto, and the handler makes its one call into a service.

Two headers carry the caller's agent and session. Handlers read them for checks like making sure a writer archives only the reviewers on its own task.

## CLI and MCP

At startup, komrad walks the compiled proto descriptors and builds the CLI and the MCP tools from them, with no generated code. It makes one <Command path="rpc" /> subcommand per method, with a flag per field, and one MCP server per agent role that holds only the tools that role may use. A tool call is a JSON post to the same route the panel uses, so the handler sees the same request either way.

## Docs and drift

`cmd/gen-docs` walks the same descriptors and writes the JSON that the [API reference](../../api/) renders. The generated files are committed. CI regenerates everything and fails if anything changed, so a proto edit that skips regeneration fails the build and the docs stay in step with the code.
