Run these from a komrad checkout, with AWS credentials from the komrad profile or in your environment. The mise tasks read the instance and its region from Terraform's state.

## Getting a shell

The machine has no SSH. Shells go through AWS Systems Manager, which needs the Session Manager plugin for the AWS CLI. Read the instance's id from Terraform, then open a session:

```sh
mise run infra:engine:run output instance_id
aws ssm start-session --target i-0123456789abcdef0
```

The session runs as a user with sudo. To act as the account komrad and its agents run as, which owns the config, the worktrees and the CLIs' logins:

```sh
sudo -u komrad -i
```

## Checking engine health

The dot beside the engine's name in the panel turns red when the engine's heartbeat stops. Open a shell and list the units that failed. A healthy engine lists none:

```sh
systemctl list-units --state=failed --no-legend
```

Then check the server and Caddy. The journal shows what systemd saw, such as a crash at startup or a failed certificate request. Komrad's log shows what the server wrote while it ran.

```sh
systemctl status komrad caddy
journalctl -u komrad -n 200 --no-pager
journalctl -u caddy -n 200 --no-pager
tail -n 200 /var/lib/komrad/cache/komrad.log
```

To list the agents, list the windows on komrad's tmux server as the komrad account:

```sh
tmux -L komrad list-windows -a
```

## Sign-in failures

When the engine rejects a person's token, their panel tells them to sign in again:

```sh
komrad login --engine remote
```

If the engine still rejects them, they have no grant. Check that the email they signed in with matches the granted email, and that their provider has verified it.

## Restarting

`mise run remote:restart` restarts the server and leaves every agent running. If the engine is stopped, it starts the machine instead.

`mise run remote:restart --hard` also kills the tmux server and creates a new manager session, which stops every agent. Use it only when the tmux session is broken.

People stay signed in through a restart, and their panels reconnect when the server is back.

## Deploying or rolling back

Releases deploy automatically. To deploy your checkout's build, run `mise run remote:deploy`. [Releases and deploys](../deploys/#deploys) describes what it does, including the case of uncommitted changes.

To roll back, deploy an older ref. From a checkout, check out the ref and run `mise run remote:deploy`. Without AWS credentials, dispatch `engine.yml` from the Actions tab on the tag or branch you want.

## Stopping and starting

```sh
mise run remote:stop
mise run remote:start
```

Stopping asks for confirmation, because every agent on the machine stops. The data volume, the database and the address survive. Starting waits until the machine passes its health checks. Resume the agents you need from the panel.

The `engine stop` and `engine start` workflows run these on a schedule, at 10pm and 7am New York time. You can also dispatch them by hand.

## Moving to a new image

Dispatch `image.yml` from the Actions tab to build an image. Then, when the agents can stop:

```sh
mise run remote:reimage
```

It lists the agents that will stop and asks for confirmation. Without an argument it uses the image `image.yml` last recorded. To use an image you built with `mise run packer:build`, pass its id. [Releases and deploys](../deploys/#image-updates) describes what changes.

## Granting and revoking access

In a shell on the machine:

```sh
sudo komrad-access grant someone@example.com
sudo komrad-access revoke someone@example.com
```

[Access](../engine-access/#access-grants) describes what a grant allows.

## Rotating the GitHub App key

Generate a new private key in the App's settings and store it in the `komrad/github-app` secret, under `private_key`. Then, in a shell on the machine:

```sh
sudo systemctl restart komrad-github-key
```

Check that <Command path="github token" /> still prints a token as the komrad account, then delete the old key from the App.

## Tearing it down

```sh
mise run infra:engine:destroy
```

Terraform can't destroy the database while deletion protection is on. Set `database_deletion_protection = false` in `terraform.tfvars` and apply before you destroy. RDS keeps a final snapshot of the database, and the data volume keeps one too. Snapshot names can't repeat, so a second teardown needs a new snapshot name.
