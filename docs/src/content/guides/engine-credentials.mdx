A remote engine's agents push code, open pull requests and call model providers. Each of those needs a credential. The control plane holds every long-lived one. Agents on a box get either a placeholder the control plane swaps for the real credential, or a key that ends with its task.

This guide covers each credential on [komrad's engine](../komrads-engine/). Another engine needs the same credentials, kept in whatever secret store and encryption service its provider offers. [Standing up an engine](../standing-up-an-engine/#rotating-credentials) covers rotating them.

## Where each credential lives

The control plane keeps three keys in Secrets Manager: the GitHub App's private key, the OpenAI admin key, and the key it signs model assertions with. Its role reads each one by its exact name, and an operator stores them by hand.

People's GitHub logins arrive while the engine runs, so they live in the database instead. Each one sits in the person's record, encrypted with a KMS key that only the control plane's role can use. The encryption names the person's sign-in issuer and subject, so a login copied to another person's record fails to decrypt.

Workers get one more credential each: an OpenAI key for their task, kept only on the worker. Dev boxes keep the person's own Claude and Codex logins in their home.

## The forge proxy

Git and `gh` on a box reach GitHub at its usual addresses, so remotes stay `https://github.com/...`. The runner starts everything that runs on a box under the agent account: panes, shells, editor connections, setup commands and hooks. Each one gets `HTTPS_PROXY` set to the runner, and the box's system git config names the runner as git's proxy too. The runner takes the connection for `github.com` and `api.github.com` with a certificate from its own authority, which the box trusts. The runner makes that authority on first boot, and only the runner's account can read its key. Connections to any other host pass through the runner untouched. `NO_PROXY` names the Anthropic and OpenAI hosts, so model calls skip the runner.

The box's git credential helper and `GH_TOKEN` both hand out a placeholder. The runner strips it and sends the request over its stream. The control plane adds the real credential and sends the request to GitHub. The firewall lets only the runner's account reach the control plane, so every forge request from a box passes through the forge proxy.

## Workers' forge tokens

The bot is a GitHub App. For each request from a worker, the control plane uses an installation token that lasts an hour and covers only the task's repository set. A bot workflow's orchestrator gets a token for the workflow's repository set instead. GitHub enforces that list on every call.

The token carries the permissions komrad's own forge calls and an agent's `gh` use need. The aim is write access to contents, pull requests, issues and workflows, and read access to actions, checks, statuses and metadata.

### Registering the App

Register the App with the permissions above. Install it only on the repositories the engine should work in. Store its private key in Secrets Manager as `komrad/github-app`, as JSON with the key under `private_key`.

The <Setting path="github_app" label="[github_app]" /> table in the control plane's config names the App's id and its installation id. The server reads the key from Secrets Manager each time it starts. Connect the server to GitHub with <Command path="forge connect" args="github.com --method github-app --engine remote" />.

## People's GitHub logins

Agents on a dev box act as their person, with everything that person can reach on GitHub, private repositories and other organisations included. An organisation that restricts OAuth apps, which GitHub does by default for new organisations, refuses the login until one of its owners approves the OAuth app. An organisation that uses SAML single sign-on also asks the person to authorize the login for it. That reach comes from the person's own login, since a GitHub App's tokens stop at the repositories it is installed on. Komrad registers a GitHub OAuth app beside the App for this, with the `repo`, `read:org` and `workflow` scopes.

The first time a person's agents or panel need GitHub, the panel shows a code and a GitHub address. The person enters the code there once, and the control plane stores the login it gets back. GitHub drops a login after a year without use, and the panel then asks the person to authorize again. Revoking the person's grant deletes their login, and so does GitHub rejecting it.

## Komrad's own forge calls

Komrad calls GitHub itself too, to read pull requests, merge them and read checks. Each call uses the credential of whoever it acts for.

A call from a worker uses its task's installation token, and komrad refuses a repository outside the task's set. A call from a dev box, or from a person in the panel, uses that person's login. Only unattended work on the control plane, such as pull request sync, uses the App's token for the whole installation.

## Commit authors

A worker's git config names the App's bot account, `<bot user id>+<app slug>[bot]@users.noreply.github.com`, so the bot authors every commit a worker makes. `gh api /users/<app slug>[bot]` prints the bot user's id.

On a dev box, the runner writes the person's name and email from their GitHub profile into their git config. A private email falls back to the person's noreply address. The person's dotfiles can override both.

## Claude on workers

Workers get Claude access through Anthropic's workload identity federation.

The control plane signs short identity assertions with its signing key. Each assertion starts with the engine's name, then names the worker's task, or the workflow on an orchestrator's worker. Each one works once. The runner keeps one assertion file for each agent and rewrites it every minute with a fresh assertion from the control plane. Claude Code reads the file, trades the assertion with Anthropic for a key that lasts a short time, and keeps that key only in memory.

Each pane on a worker gets `ANTHROPIC_IDENTITY_TOKEN_FILE`, `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID` and `ANTHROPIC_WORKSPACE_ID`.

An operator registers the control plane as an issuer once, in the Anthropic Console, with its public key pasted in. One federation rule matches every worker by the engine's name at the start of its subject.

## Codex on workers

The bot has one service account in an OpenAI project. For each task, the control plane creates an API key under that account and hands it to the worker's runner, which gives it to Codex. Deleting the task deletes the key, and archiving it revokes the key. Restoring the task creates a new one. An orchestrator's worker gets a key of its own on the same terms, made with the worker and revoked or deleted with its workflow. The aim is for each key to expire on its own and carry only the permissions Codex needs, where OpenAI's API allows it. The OpenAI admin key that creates them stays on the control plane.

## Models on dev boxes

A person's agents use the person's own Claude and Codex logins. Sign in once in a shell on your dev box, and the logins stay in your home.

## GitLab

The forge proxy serves GitHub. A workflow on GitLab runs on a local engine, which uses the laptop's own credentials.
