This guide replicates [komrad's engine](../komrads-engine/) in an AWS account of your own. It builds the same architecture from an empty account, with each step in the order the later ones depend on, and then covers the routine jobs of running it. The Terraform, the Packer template and the mise tasks are the ones komrad's own engine runs on, so a different architecture means changing them first. Run every command from a komrad checkout. The mise tasks use the AWS profile named komrad unless your environment already has credentials.

## Prerequisites

A replica needs its own account with each service komrad's engine depends on:

- An AWS account with a named profile, and an S3 bucket for Terraform's state.
- The Session Manager plugin for the AWS CLI, which you need to get a shell on the machine.
- A Tailscale tailnet you administer, with Tailscale running on your laptop.
- Komrad registered with your identity provider as a desktop app. [Komrad's engine](../komrads-engine/#provider-registration) covers the registration.
- A GitHub App for the engine, with its private key stored in Secrets Manager as `komrad/github-app`. [Komrad's engine](../komrads-engine/#github) covers the App. The machine reads the key at boot, so store it before the first one.

## Building the image

```sh
mise run packer:build
```

The build prints the image's id when it finishes, and Terraform needs that id in the next step. [Komrad's engine](../komrads-engine/#the-image) describes what the image contains.

## Preparing the tailnet

The engine joins your tailnet as one tagged device, and the rest of the tailnet stays as it is. In Tailscale's admin console:

1. Under DNS, turn on MagicDNS and HTTPS certificates. The tailnet's DNS name, such as `tail1234.ts.net`, is at the top of the page.
2. In the access policy, add `tag:komrad-engine` to `tagOwners`, as [komrad's engine](../komrads-engine/#the-tailnet-policy) shows.
3. Under Settings, then Keys, generate an auth key. Make it single-use and pre-approved, and tag it `tag:komrad-engine`. The engine uses it only to join the first time, so a key that expires in a day is enough.

## Applying the infrastructure

Copy `terraform.tfvars.example` and `backend.hcl.example` in [`infra/engine`](https://github.com/harrisoncramer/komrad/tree/main/infra/engine), remove the `.example`, and fill them in. The variables include your account, the region, the image id, and the `sign_in_*` values from your provider. Set `tailscale_hostname` to the engine's name on the tailnet, which defaults to komrad, and `tailscale_tailnet` to your tailnet's DNS name, such as `tail1234.ts.net`. Set `tailscale_auth_key` to the auth key from the last step, which Terraform stores in Secrets Manager for the machine. GitHub Actions needs the `github_*` values and `state_bucket` to deploy. Then run:

```sh
mise run infra:engine:init
mise run infra:engine:apply
```

The apply prints the engine's address as `engine_url`, its instance id as `instance_id`, and the CI role as `ci_role_arn`.

On first boot, the machine joins the tailnet with the auth key, mounts its data volume, migrates the database, creates the engine's login, and starts the server and Caddy. The key is spent once the machine joins.

Open a session and check that no unit failed. On a healthy machine the second command prints nothing:

```sh
aws ssm start-session --target i-0123456789abcdef0
systemctl list-units --state=failed --no-legend
```

## Configuring GitHub Actions

Komrad's release and image workflows deploy to its engine. In your copy of the repository, they reach your engine through these repository variables:

- `AWS_CI_ROLE`, from the `ci_role_arn` output
- `AWS_REGION`
- `TF_STATE_BUCKET`
- `TF_STATE_KEY`, matching the key in your backend file

If you changed the stack's `name`, set `ENGINE_NAME` to match. The workflows skip their engine steps until `AWS_CI_ROLE` is set.

## Configuring the engine

In a session on the machine, switch to the komrad account, which owns komrad's config:

```sh
sudo -u komrad -i
```

Edit `~/.config/komrad/config.toml`:

- Add the <Setting path="github_app" label="[github_app]" /> table with the App's id, its installation id, and `/run/komrad/github.pem` as the key's path.
- Turn on <Setting path="harness.claude.trust_launch_dirs" label="trust_launch_dirs" /> for each agent CLI, so new agents don't stop to ask whether to trust their worktree.

Check that <Command path="github token" /> prints a token. Then restart the server so it loads the new config, as [restarting](#restarting) shows.

Still as the komrad account, start each agent CLI once and sign it in, and clone the repositories the agents will work in. The logins and the clones live on the data volume, so they survive when the instance is replaced.

## Granting your own access

Exit the komrad account's shell and grant yourself access:

```sh
sudo komrad-access grant you@example.com
```

Check that your tailnet policy lets you reach the engine on 443. Then, on your laptop, create `~/.config/komrad/engines/remote.toml` with the `engine_url` the apply printed:

```toml
[connection]
url = "https://komrad.tail1234.ts.net"
```

Sign in and open the panel:

```sh
komrad login --engine remote
komrad open --engine remote
```

## Connecting the forge

From your laptop, run <Command path="forge connect" args="github.com --method github-app --engine remote" />. The server mints its own tokens from the App's key, so you have nothing to paste. To connect GitLab too, follow [komrad's engine](../komrads-engine/#gitlab).

## Running the engine

These jobs keep komrad's engine running, and they work the same on a replica. Run them from a komrad checkout, with AWS credentials from the komrad profile or from your environment. The mise tasks look up the instance and its region in Terraform's state.

### Getting a shell

You get a shell on the machine through AWS Systems Manager, which needs the Session Manager plugin for the AWS CLI. Look up the instance's id in Terraform, then open a session:

```sh
mise run infra:engine:run output instance_id
aws ssm start-session --target i-0123456789abcdef0
```

The session runs as a user with sudo. Switch to the komrad account to work as komrad and its agents do. That account owns the config, the worktrees and the CLIs' logins:

```sh
sudo -u komrad -i
```

`mise run remote:connect` opens the session and switches to the komrad account in one step.

### Checking engine health

When the engine's heartbeat stops, the dot beside its name in the panel turns red. Open a shell and list the failed units. On a healthy engine the command prints nothing:

```sh
systemctl list-units --state=failed --no-legend
```

Then look at Tailscale, the server and Caddy. `tailscale status` shows whether the machine is on the tailnet. The journal shows what systemd saw, like a crash at startup or a certificate request that failed. Komrad's log shows what the server wrote while it ran.

```sh
sudo tailscale status
systemctl status tailscaled komrad caddy
journalctl -u tailscaled -n 200 --no-pager
journalctl -u komrad -n 200 --no-pager
journalctl -u caddy -n 200 --no-pager
tail -n 200 /var/lib/komrad/cache/komrad.log
```

To see the agents, list the windows on komrad's tmux server as the komrad account:

```sh
tmux -L komrad list-windows -a
```

### Sign-in failures

When the engine rejects someone's token, their panel asks them to sign in again:

```sh
komrad login --engine remote
```

If the engine still turns them away, they don't have a grant. Check that the email they signed in with is the one you granted, and that their provider has verified it.

If their panel says the engine is unreachable, check that Tailscale runs on their laptop with DNS on and that the tailnet policy lets them in.

### Rejoining the tailnet

A replaced machine keeps its tailnet identity through Parameter Store. If someone removes the engine from Tailscale's admin console, it drops off the tailnet and needs a new key. Set `tailscale_auth_key` to a new single-use, pre-approved key tagged `tag:komrad-engine` and run `mise run infra:engine:apply`. Then join again in a shell on the machine:

```sh
sudo systemctl restart komrad-tailscale
```

### Restarting

`mise run remote:restart` restarts the server and leaves the agents running. If the engine is stopped, it starts the machine instead.

`mise run remote:restart --hard` also kills the tmux server and creates a new manager session, which stops every agent. Save it for when the tmux session itself is broken.

People stay signed in through a restart, and their panels reconnect once the server is back.

### Deploying or rolling back

Releases deploy on their own. To deploy the build in your checkout, run `mise run remote:deploy`.

To roll back, deploy an older ref. Either check it out and run `mise run remote:deploy`, or, without AWS credentials, dispatch `engine.yml` from the Actions tab on the tag or branch you want.

### Stopping and starting

```sh
mise run remote:stop
mise run remote:start
```

Stopping asks you to confirm, because it stops every agent on the machine. The data volume, the database and the address stay. Starting waits until the machine passes its health checks, and then you resume the agents you need from the panel.

### Moving to a new image

Dispatch `image.yml` from the Actions tab to build an image. When it's fine for the agents to stop, run:

```sh
mise run remote:reimage
```

The task lists the agents that will stop and asks you to confirm. With no argument it uses the image `image.yml` recorded last. To use an image you built yourself with `mise run packer:build`, pass its id.

### Granting and revoking access

In a shell on the machine:

```sh
sudo komrad-access grant someone@example.com
sudo komrad-access revoke someone@example.com
```

A person also needs to reach the engine over the tailnet. Check that your policy lets them reach it on 443, or share the engine with them from Tailscale's admin console if they're outside your tailnet.

[Komrad's engine](../komrads-engine/#access-grants) describes what a grant allows.

### Rotating the GitHub App key

Generate a new private key in the App's settings and store it in the `komrad/github-app` secret, under `private_key`. Then, in a shell on the machine:

```sh
sudo systemctl restart komrad-github-key
```

As the komrad account, check that <Command path="github token" /> still prints a token, then delete the old key from the App.

### Tearing it down

```sh
mise run infra:engine:destroy
```

Terraform can't destroy the database while deletion protection is on, so set `database_deletion_protection = false` in `terraform.tfvars` and apply before you destroy. RDS takes a final snapshot of the database, and the data volume gets one too. Snapshot names have to be unique, so a second teardown needs a new snapshot name.

Then remove the engine from Tailscale's admin console and delete its tailnet identity. Terraform doesn't own the parameter, and its path is `/<name>/tailscale/state` for the stack's `name`:

```sh
aws ssm delete-parameter --name /komrad-development/tailscale/state
```
