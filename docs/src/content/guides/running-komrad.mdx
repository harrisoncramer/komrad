Komrad has two halves. The panel is what you look at. The engine does the work. It runs the server and the agents, keeps the agents' worktrees on disk, and records everything in Postgres. On a laptop both halves run on the same machine, and nobody else can reach them. [Installing komrad](../install/) covers that setup.

A remote engine runs on a machine that stays on, and the panel stays on your laptop. Agents keep working while the laptop sleeps, and several people can use the same engine. This guide describes the parts a remote engine needs, without assuming a cloud provider. [Our engine](../our-engine/) describes how we run ours on AWS.

The panel signs in with an identity provider, then sends its requests over HTTPS to the engine host. An HTTPS proxy on the host holds the certificate and forwards each request to the server over loopback. The server records everything in Postgres and reads pull requests from the forge.

The agents run in a tmux server that komrad starts for itself. They edit their worktrees on disk, call the server through komrad's MCP tools, and push branches to the forge with git.

The host needs Linux, tmux, git, the agent CLIs and komrad. The server runs as a service under an account that can't become root, because agents run whatever commands they choose.

## State

An engine keeps its state in two places. Postgres holds every record: workflows, tasks, agents, mail, reviews and transcripts. A disk holds the worktrees, the agent CLIs' logins and komrad's config.

Keep both off the host, in a database server and on a separate volume. You can then replace the host and lose only the processes that were running on it. Agents that stopped can be resumed.

Restarting the server doesn't stop the agents. Their tmux server keeps running while the komrad server restarts, and the new server finds the agents where the old one left them.

## Access to a remote engine

A remote engine checks who sent each request. People sign in with an identity provider that supports OpenID Connect, such as Google or Okta, so komrad stores no passwords. The engine then checks that its owner granted that person access. A grant gives full access, including a shell on the host as the account agents run as. [Access](../engine-access/) covers sign-in and grants.

The server never listens on the network itself. The HTTPS proxy holds the certificate and forwards requests to it over loopback. We use Caddy, which gets and renews its own certificate. Any proxy that supports HTTP/2 works.

Operators also need a shell on the host. That shell must not be reachable from the internet.

## Forge credentials

Agents push branches and the server reads pull requests, so the engine needs credentials for each forge. A personal token works on a laptop. On a shared engine, a personal token makes every agent act as one person, and it stays valid on disk until it expires. Give a shared engine credentials of its own that expire quickly. [Forge credentials](../forge-credentials/) covers GitHub and GitLab.

## Requirements

- A Linux host that stays on, with tmux, git, the agent CLIs and komrad.
- A volume for the worktrees and logins that outlives the host.
- A Postgres database the host can reach.
- A domain name and an HTTPS proxy.
- An identity provider with komrad registered on it.
- Forge credentials that belong to the engine.
- A way for operators to get a shell that isn't reachable from the internet.

[Standing up an engine](../standing-up-an-engine/) builds all of this on AWS.
