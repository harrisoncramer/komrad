[Agents](../agents/) on your laptop stop when your laptop sleeps. Komrad can run them on a remote engine instead. The panel stays on your laptop and looks the same. The server and the database move to the engine's control plane, and every agent runs on one of its boxes.

Komrad's own repository works this way.

## Connecting

An engine is a small config file on your laptop in `~/.config/komrad/engines/`, named after the engine. Its <Setting path="connection" label="[connection]" /> table names the engine's <Setting path="connection.url" label="url" />, the HTTPS address it answers on, and the panel does everything on the engine through the API there:

```toml
[connection]
url = "https://komrad.tail1234.ts.net"
```

An engine on a tailnet needs Tailscale running on your laptop with DNS on.

## Signing in

The engine lets in only people an operator granted access. Sign in once per engine, with the email the operator granted:

```sh
komrad login --engine remote
```

A browser opens at the engine's identity provider. You can also open the panel and press enter at its sign-in screen. The panel stays signed in after that. It asks again after a long time away, or after your access ends. [Komrad's engine](../komrads-engine/#access) covers how the sign-in works and what the engine checks.

## Switching engines

<Command path="open" /> opens your laptop's panel. <Command path="open" args="--engine remote" /> opens the engine named
`remote`, and `--engine local` names your laptop.

Every panel shows which engine it is on at the top of the sidebar, with the release its server runs, or its commit when it runs no release. The dot beside it is green while the engine's heartbeat arrives, and red once it stops. The message it flashes beside the engine says why, and <Key name="messages.open" /> opens the whole message with what to do.

To move to another engine, close the panel and run <Command path="open" args="--engine" /> with that engine's name.

## Your workflows and the bot's

Every workflow on a remote engine has a workflow owner, you or the bot. The panel lists your own workflows and the bot's.

Your own workflows run on your dev box, a box that belongs to you alone. Their agents act as you, with your GitHub access. An operator adds your dev box. You start and stop it from the panel, and it keeps your home, your worktrees and your logins while it is stopped.

The first time your agents or the panel need GitHub, the panel shows a code and a GitHub address. Enter the code there once, and the engine acts as you on GitHub from then on.

A bot workflow runs each task on a worker of its own. Its agents act as the bot, on only the repositories the workflow names. When the engine already runs as many workers as it allows, a new bot task waits as queued and starts once another worker stops. [Running komrad remotely](../running-komrad-remotely/#workflow-owners) covers where each kind of workflow runs.

## Attaching to an agent

An agent's terminal on its box is streamed to your panel, and <Command path="terminal" args="AGENT" /> does the same in any terminal. The agent's window takes the size of the terminal attached to it, so it fills the stage and follows it when you resize.

The terminal in an agent's [menu](../navigation/#the-menu) works the same way. It opens a shell on the agent's box, in the agent's directory there, and streams it to the pane below the stage.

One exception is a window someone fixed at a size on the box itself, by running tmux's `resize-window`, which sets the window's `window-size` to `manual`. That window keeps its size wherever it attaches, so a smaller terminal crops it and a larger one leaves blank space around it.

## Editing files on the engine

Every agent's files live on its box, so your editor opens them there. <Command path="login" /> writes an SSH host for the engine in `~/.ssh/komrad/`, named `komrad-` and the engine's name, such as `komrad-remote`. SSH to that host travels through the engine's API on your sign-in.

The host reaches your dev box. To reach a bot task's worker, put the task's slug before the host as the SSH user, such as `fix-login@komrad-remote`. The engine starts the worker if it is stopped.

The edit keys use that host and pick the agent's box for you. <Key name="menu.edit" /> on an agent and <Key name="review.edit_file" /> in a review open the file with your `$EDITOR`. A terminal editor such as `nvim` runs on the box, in the pane beside the stage, so the box needs that editor installed. VS Code, Cursor and Zed open a window on your laptop that edits the box's files over the same host, once your `~/.ssh/config` includes it as below. Sublime Text and JetBrains editors cannot open files on another machine, so the edit keys refuse them.

To reach the engine from any other program, such as `ssh` or your editor's remote window, add this line to the top of `~/.ssh/config`:

```
Include ~/.ssh/komrad/*.conf
```

Then `ssh komrad-remote` opens a shell on your dev box. <Command path="login" /> prints the line when your `~/.ssh/config` lacks it.

## Agent CLI logins

Agents on your dev box use your own Claude and Codex logins. Open a shell on your dev box, start each CLI once and log in. The logins live in your home.

The engine gives each worker its model access, as [credentials on an engine](../engine-credentials/#claude-on-workers) describes.

## Dotfiles

Your dev box can carry your dotfiles. Name the repository and the command that installs it in a `[dotfiles]` table in the engine's file on your laptop, then run `komrad dotfiles --engine remote`. Komrad clones the repository into your home on the dev box as you, and runs the install command in a login shell there. It refuses when your dotfiles on the box have changes you haven't pushed, or come from a different repository.

A `.gitconfig` in your dotfiles must leave the box's credential helper alone, or git on the box stops reaching GitHub. If your dotfiles switch shells, guard the line so it only runs in a terminal, such as `[ -t 1 ] && exec zsh`. Install your editor through your global mise config, so it is on the box for the edit keys.

## Project tools

Boxes carry mise. A repository pins the languages it needs, such as Go and Node, in a `mise.toml` or `.tool-versions`, and its workflow names `mise install` as its [setup command](../workflows/#worktrees).

Your dev box keeps what it installs, so only the first task to ask for a version waits while it downloads. Each worker starts empty and installs what its own task needs, which can take a minute or two.

## Stopped engines and boxes

An engine costs money every hour, so parts of it may be switched off while idle.

A stopped dev box keeps its home and worktrees. Its agents stop, and you resume the ones you want once you start it again. Your workflows' schedules skip their runs while it is stopped.

A worker stops on its own once every agent on it has been dormant for a while. Resuming one of its agents, or sending it mail, starts the worker again.

An operator can also stop the whole engine. That keeps every volume, the database and the address, and stops every agent.

This guide covers using an engine. [Running komrad remotely](../running-komrad-remotely/) covers building one.
