A remote engine accepts requests from people it can identify and that its owner has let in. People sign in with an identity provider, and the engine checks a grant for each of them. Operators reach the machine through a separate path that never touches the internet.

## Signing in

Each person signs in once per engine, from their laptop:

```sh
komrad login --engine remote
```

Komrad asks the engine which identity provider it trusts and opens a browser there. The person signs in at the provider, including any MFA it requires. The provider sends the browser back to komrad on `127.0.0.1:8085` with a one-time code, and komrad exchanges the code for two tokens.

The ID token lasts about an hour, and the panel sends it with every request. The refresh token gets a new ID token without opening the browser. Komrad keeps both in the system keychain. The panel refreshes the ID token before it expires, including during an open terminal session. When the refresh token stops working, the panel tells the person to sign in again.

Komrad never sees the person's password.

## Request checks

The public listener checks every request it receives. A token must be signed by the provider the engine trusts, must have been issued for komrad, and must not have expired. A request that fails any of these checks gets a 401.

The listener then checks that the person holds a grant on this engine. A request without one gets a 403. A request that passes carries the person's identity into the handler and the log.

## Access grants

<Command path="engine grant" /> gives a person access by their email address, and <Command path="engine revoke" />
removes it. The first time a granted person signs in with a verified email, the engine records the permanent id their
provider uses for that account, and matches on that id from then on.

Access is all or nothing. A granted person can do everything the panel does, including opening a shell on the machine as the account agents run as. Grant access only to people you would give a login on the machine.

The engine caches each grant for one minute. A revoke takes effect within a minute, including on open terminal sessions. If the engine can't reach the database to check a grant, it refuses the request.

Both commands connect as the database owner, so on our engine they run as root. [Runbooks](../runbooks/#granting-and-revoking-access) shows the commands.

## Registering komrad with the provider

The engine's owner registers komrad with their identity provider once, as a desktop app, with `http://127.0.0.1:8085` as the redirect address. The provider issues a client id. The engine's config names the provider and that client id.

Google also issues a client secret. Every copy of komrad carries it, so it protects nothing, but Google requires it, so it goes in the config too. On Google, publish the app or make it internal to your Workspace. An app left in testing mode makes everyone sign in again every week.

## Server listeners

The server listens on two loopback addresses. Neither is reachable from the network directly.

The public listener receives people's requests from Caddy and checks each one as described above. It serves the API and one public page that tells a panel which identity provider to use. It doesn't serve komrad's MCP endpoint, and it ignores the headers that identify an agent, so a person can't act as an agent.

The loopback listener serves the agents, their MCP tools, and the CLI in a shell on the machine. It doesn't check identity, because only processes on the machine can reach it.

## Network

Port 443 is open to the internet, and the token is what protects it. An owner with fixed office or VPN addresses can restrict 443 to those addresses. Port 80 is open for Let's Encrypt's certificate check, and Caddy redirects every other request on it to HTTPS. No other port is open.

## Operator and CI access

Operators reach the machine through AWS Systems Manager. It needs no open port and no keys on the machine. A session opens a shell as a user with sudo, and `sudo -u komrad -i` switches to the account agents run as. Deploys and restarts send commands through Systems Manager too, from a laptop or from GitHub Actions.

Anyone whose AWS credentials can open a session or send a command to the instance has root on it. Protect those credentials accordingly.
