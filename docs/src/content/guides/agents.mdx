Agents perform work in komrad. Each one is a real Claude or Codex session running in a terminal that komrad manages for you. Agents are designed to be stateless in komrad, so that you can easily create or discard them without losing work.

<Alert variant="warning">
  This guide assumes you know what a [workflow](../workflows/) and a [task](../tasks/) are.
</Alert>

They are also durable. You can shut down or restart your machine without losing any history or context with an agent, and easily restore or search through their conversations later. Agents can also start and manage other agents.

## Three kinds of agent

Komrad has three kinds of agents.

There is always one _orchestrator_ agent per [workflow](../workflows/#the-orchestrator). The orchestrator is rendered above the workflow's tasks, and coordinates the work across them.

Every task has exactly one _writer_. The writer does the task's work: it makes edits, commits, and opens the pull request. It is the only agent that changes the task's checkout, and it stays with the task for the task's whole life. You can [restart](../tasks/#restarting-the-writer) it on a new conversation whenever you want, for instance if you want to switch the model working on the task from Claude to Codex.

Finally, _reviewer_ agents read the writer's change and comment on it. Reviewers work in the task's checkout but make no changes of their own.

```
  workflow: neovim
   |-- orchestrator                <-- coordinates the workflow's tasks
   |
   |-- task: fix-login (writer)    <-- the writer does the work, owns the checkout
   |      '-- reviewer             <-- reads the writer's change
   |
   '-- task: rfc-truncate (writer)
```

The list draws the same tree. A task and its writer share one row under the workflow, and the task's reviewers sit beneath it.

## Reviewers

Reviewers are created to review the work performed by writers. Writers will spawn them when their work is ready. The reviewer reads the change and leaves comments on its lines, the same way you do in a [review](../reviews/), and the writer answers them. While a reviewer is still reading, the writer cannot ask for another. Over a task's life it can go through many reviews.

You can start a reviewer yourself too. Open a task's menu and pick new agent with <Key name="menu.new_agent" />, then say what you want looked at. The orchestrator can also spawn reviewers for tasks.

Set <Setting path="usage.task.max_reviewers" /> to cap how many reviewers one task can hold at a time.

Komrad archives a reviewer once it approves. Turn off <Setting path="usage.reviewer.archive_on_approval" /> to keep approved reviewers in the list until you archive them yourself.

## Adopting work

Sometimes the work started outside komrad, such as a colleague's pull request or a branch you began on another machine. Hover the workflow, open the menu with <Key name="menu.open" /> and press <Key name="menu.adopt" />. Name the branch and say what to do with it. Komrad starts a task on that branch with a writer on it, in a worktree of its own when the workflow cuts them.

The branch has to be in the workflow's repository, either pushed to its origin or already on disk.

## Archiving and deleting an agent

Archiving an agent stops it and takes it out of the list. Its conversation stays in the database, so you can still search it or restore it later.

A writer and its task share one life, so you never archive a writer on its own. Archive the [task](../tasks/#archiving-restoring-and-deleting-tasks) instead, which archives the writer and every reviewer on it. Restoring the task brings its writer back.

Reviewers come and go on their own. You can archive one whenever you like, and restore it later once its task is live. Deleting an archived reviewer is permanent and removes its conversation. A writer is deleted only with its task.

## How komrad knows what an agent is doing

Most agent tools learn what an agent is doing from hooks the agent fires. Hooks can be dropped, reordered, or never sent, for example when the CLI crashes. There are lots of bug reports on other agent orchestrators outlining this exact problem.

Komrad takes a different approach. It reads each agent's state directly from what its terminal actually renders, which komrad calls the pane. The [Claude test panes](https://github.com/harrisoncramer/komrad/tree/main/internal/harness/claude/testdata) show what it reads.

If Claude or Codex ever ship real-time state notifications, komrad will move to them! Until then, reading the pane is the more reliable choice.

If the state shown does not match your CLI, please <a href={link('/guides/bug-reports')}>submit an issue</a> on GitHub with the pane that's missing/wrong.
