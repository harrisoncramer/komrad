A remote engine sits on the internet, so it has to know who's knocking. Komrad doesn't keep passwords of its own for this. It leans on an identity provider you already trust, such as Google or Okta, and on a short list of people the engine's owner has let in.

## Signing in

Each person signs in once per engine, from their own laptop:

```sh
komrad login --engine remote
```

That opens a browser at the identity provider. You sign in there the way you would anywhere else, MFA and all, and the browser hands komrad a token proving who you are. Komrad keeps it in your system keychain and sends it along with every request. It quietly swaps it for a fresh one before it expires, so you shouldn't have to sign in again unless you've been away a long time or someone took your access away.

Komrad never sees your password. The provider vouches for you, and the engine checks that the token really came from the provider it trusts and really was meant for komrad.

## Who may use an engine

Proving who you are isn't enough to get in. The engine's owner also has to grant you access, by email, with <Command path="engine grant" />. <Command path="engine revoke" /> takes it away again, and an engine notices within a minute, even if you have a terminal open at the time.

Access is all or nothing. Anyone you let in can do everything the panel can, including opening a shell on the machine as the account the agents run as. Grant it the way you'd hand someone a login to the machine itself.

On our engine, both commands need root, so they run from a shell on the machine. [Runbooks](../runbooks/#granting-and-revoking-access) shows how.

## Registering komrad with the provider

Before anyone can sign in, the engine's owner registers komrad with their identity provider once, as a desktop app, with `http://127.0.0.1:8085` as the address to send people back to. The provider gives you a client id, which goes in the engine's config along with the provider itself.

Google also hands you a client secret. For a desktop app it isn't really secret, since every copy of komrad carries it, but it still has to go in the config. If you're on Google, publish the app or make it internal to your Workspace. An app left in testing mode makes everyone sign in again every week.

## Behind the scenes

The server listens in two places, both on the machine itself, so neither is reachable from outside on its own.

The public listener is where people's requests end up. Caddy holds the certificate and passes each request through, and the public listener checks every one for a valid token and a grant. It deliberately leaves out the parts of komrad that only agents should use.

The loopback listener is for things already on the machine, like the agents and their tools. It doesn't ask who's calling, because getting to it at all means you're already on the machine.

## Operators and CI

Whoever runs the machine gets in through AWS Systems Manager rather than SSH. Systems Manager needs no open port and no keys on the machine, and every session is tied to someone's AWS credentials. Deploys and restarts, whether you run them from your laptop or GitHub Actions runs them, go the same way.

That makes those AWS credentials the real keys to the machine. Anyone who can open a session or send the instance a command has root on it, so treat them accordingly.
