Every message an agent receives is _mail_. Some of it comes from other agents, and some comes from komrad itself when something the agent cares about changes. Both kinds arrive the same way. Komrad sends its own mail through a [transactional outbox](#how-a-change-becomes-mail), so mail always follows a saved change, and komrad never sends mail for an unsaved one.

## Messages between agents

Agents talk to each other asynchronously by mail. Mail lets an orchestrator hand out work and hear back from the writers of its tasks, or a reviewer send a message back to the writer, without either pausing the other's line of thought.

### Try it

Start a task with this brief and watch the two argue.

```text
You are an avid neovim fan, and need someone to debate.
Spawn a komrad agent who loves emacs, then mail them back and forth
about the merits of the two editors, for a few rounds.
```

## How mail arrives

Mail never interrupts an agent mid-turn, except a review you send, which stops the agent so it reads your comments now. A running agent reads its mail when it finishes its turn. Komrad "nudges" an idle agent to check its mail.

Agents don't wait for replies, because mail is asynchronous. Komrad tells them to check their mail when new mail arrives.

## Limits and Expiry

Orchestrators and writers can mail each other freely, across tasks and workflows. A [reviewer](../agents/#reviewers) can mail only the agents on its own task and its workflow's orchestrator. Mail expires when it stays unread past <Setting path="mail.delivery_deadline" />.

You can limit how much mail two agents exchange by setting <Setting path="mail.max_exchange" />. It stops two agents from looping on each other forever. When the limit stops a message, the sender gets an error and komrad tells the other agent, so it does not wait for a reply that will never come. Your own mail never counts.

## Events and Mail

Komrad also mails an agent itself when something changes that the agent should hear about.

| What changed                                                         | Who is told                           |
| -------------------------------------------------------------------- | ------------------------------------- |
| The pull request's status changed: checks failed, it conflicts, etc. | The writer of each task on its branch |
| You wrote or edited a [document](../documents/) in the panel         | The agent that owns it                |
| A task's branch was rebased, force-pushed, or had a rebase aborted   | The task's writer                     |
| A [local review](../reviews/) of a task's change was released        | The task's writer                     |
| The writer answered a reviewer's threads                             | That reviewer, which is also woken    |

An agent holds at most one unread piece of mail from komrad about any one thing. If a pull request's checks fail and then its branch conflicts before the agent has read anything, the agent gets one piece of mail saying both. Later changes rewrite the unread mail instead of adding more. Once the agent has read its mail, the next change starts a new one.

## How a change becomes mail

Komrad records each change as an _event_ in the same database transaction as the change itself. If you save a document, the save and its event commit together. If the save fails, there is no event. If komrad stops a moment after the save, the event is still there when it comes back.

This pattern is called a _transactional outbox_. Komrad saves the change and the record that announces it together or not at all, and a separate worker announces the change, retrying until it succeeds. Komrad keeps its events in the same job queue it uses for other background work, and the messages land in the mail table.

```
  one transaction
  ├── the change: checks on #412 → failing
  └── the event:  "pull request #412 changed"
          |
          v  a moment later
  one transaction
  ├── the handler for pull requests finds the writers on the branch
  ├── writes or rewrites each one's mail
  └── marks the event done
          |
          v
  delivered the same way as any other mail
```

Background workers pick up and run each event.

If the mail cannot be written yet because the agent's mailbox is full, komrad tries the event again later. The change itself is never held up. Saving a document or releasing a review works even when the agent is not keeping up with its mail. Mail for an archived agent is dropped.
