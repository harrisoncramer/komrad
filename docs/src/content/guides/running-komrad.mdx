On your laptop, komrad is one program and a Postgres database. You install it, run it, and that's the whole deployment. The catch is that your agents live on your laptop too, so they stop when you close the lid, and nobody else can see them.

This guide is for when you want that to change. Maybe you want agents that keep working overnight, or a team that shares one set of agents. Either way, you're moving the agents onto a machine that stays on and keeping the panel on your laptop. Nothing here assumes a particular cloud. [Our engine](../our-engine/) shows how we did it on AWS, if you'd like a worked example.

## What moves

Komrad calls the side that does the work an engine. That's the server, the agents it runs, and the worktrees they edit. With a remote engine all of that moves to another machine, and the panel on your laptop talks to it over the network. The panel looks and behaves the same either way. [Remote engines](../remote/) covers it from the user's side.

The machine doesn't need to be anything special. Any Linux box that can run tmux, git and your agent CLIs will do. You'll want to be careful about where its state lives, though. The worktrees and the CLIs' logins sit on disk, and everything komrad knows sits in Postgres. If you keep both somewhere that outlives the machine, say a separate volume and a database the machine connects to, you can throw the machine away and build a new one whenever you like. Agents that stopped along the way pick up right where they left off once you resume them.

Restarting the server is even cheaper. Komrad keeps its agents in a tmux server of its own, and the komrad server can restart without touching it, so a deploy leaves every agent running.

## Letting people in

<figure>
  <img
    src={link("/diagrams/running-komrad.png")}
    alt="The panel signs in with an identity provider and reaches the engine host over HTTPS. On the host, an HTTPS proxy sits in front of the server and the agents. The host uses Postgres, and the agents push to the forge."
  />
</figure>

On your laptop nobody else can reach komrad, so it never asks who you are. A remote engine has to. Rather than keep passwords of its own, the engine trusts an identity provider you already use, such as Google or Okta. Each person signs in there from their laptop, and the engine checks that its owner actually let them in.

Take that last part seriously. Anyone you let in can do everything the panel can, and the panel can open a shell on the machine as the account the agents run as. So hand out access the way you'd hand out a login to the machine itself. [Access](../engine-access/) goes into sign-in and grants in more detail.

The server never faces the network directly. You put an HTTPS proxy in front of it to hold the certificate, and the proxy passes requests to the server locally. We use Caddy, because it fetches and renews its own certificate, but any proxy that speaks HTTP/2 is fine.

## Pushing code

Agents push branches and komrad reads pull requests, so the engine needs credentials for your forge. On a laptop, your own token works fine. On a shared machine it's a bad idea, because every agent would push as you and the token would sit on a disk for as long as it's valid. It's better to give the engine an identity of its own, with tokens that expire on their own. [Forge credentials](../forge-credentials/) shows how we do that for GitHub and GitLab.

## What you'll need

If you're setting one up, here's the short version:

- A Linux machine that stays on, with tmux, git, the agent CLIs and komrad installed, and a volume for the worktrees that outlives it.
- A Postgres database the machine can reach.
- A domain name, and an HTTPS proxy in front of the server.
- An identity provider with komrad registered on it.
- Forge credentials that belong to the engine rather than to a person.
- Some way for you to get a shell on the machine that isn't open to the internet.

[Standing up an engine](../standing-up-an-engine/) walks through all of it on AWS, in order.
