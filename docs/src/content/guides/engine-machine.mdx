Our engine is one Linux machine, and we try hard not to care about it. Anything worth keeping lives on a separate volume or in the database, so if the machine breaks, or we want a newer one, we build another and carry on. The only things lost along the way are whatever happened to be running at the time.

## The image

We build the machine's image with Packer, from the template in [`packer`](https://github.com/harrisoncramer/komrad/tree/main/packer). It starts from a stock Ubuntu image and layers on everything an agent might reach for: git, tmux, Docker, Go, Node, the agent CLIs, Caddy and komrad itself. Each layer is a short script, so adding a tool usually means adding a few lines to one of them.

The image does include a komrad binary, but only so the machine has something to run on its first boot. Every deploy replaces it, so we rarely need to rebuild the image for a new version of komrad. [Releases and deploys](../deploys/#a-new-image) covers when we do.

## Who runs what

The server and every agent run as a single account named komrad, and that account can't become root. That matters more than it sounds. Agents run whatever commands they decide to, so we'd rather they couldn't take over the machine, or reach the AWS credentials the machine itself uses. Docker runs without root for the same reason, which lets agents build and run containers without holding the keys to everything else.

Root work, like deploys, restarts and granting people access, comes in through AWS Systems Manager instead. Nobody logs in over SSH. [Access](../engine-access/) covers how that works.

## The data volume

Everything the machine can't afford to lose lives on its data volume: the komrad account's home, with its config and the agent CLIs' logins, every agent's worktree, komrad's cache and log, and Caddy's certificates. When we replace the machine, the volume detaches from the old one and attaches to the new one, and the agents find their work right where they left it.

When the machine boots, it mounts the data volume first. Nearly everything else waits on that, so a missing volume stops the server outright rather than letting it quietly write to the wrong disk.

Next the machine gets its credentials. It reads the database owner's password from AWS, migrates the database, and makes sure the engine has its own login, which [the database](../engine-database/) explains. It also fetches the GitHub App's key into memory, so the key never lands on a disk. Once both are ready, the server starts, and then komrad sets up the tmux session the agents live in.

Caddy starts alongside all this, once it can find its certificates on the volume. Terraform tells the machine which volume, which database and which domain are its own, and never hands it a secret, since anything on the machine can read what Terraform passes in.

## Why agents survive a restart

The server starts the tmux server that holds the agents, and normally that would make tmux part of the server's service, so stopping one would stop the other. We tell systemd to stop only the server process instead. A restart or a deploy leaves tmux, and every agent in it, running, and the new server picks them up where the old one left off.

Stopping or replacing the machine is different, and every agent stops with it. Their conversations and worktrees are still on the volume, though, so you can resume them once the engine is back.
