Komrad agents run inside of _workflows_. Workflows are just a bucket of settings: the directory for an agent to run in, the harness it'll use, like Claude or Codex, and other settings for every agent that spawns within them.

<Alert variant="warning">This guide assumes you have [installed komrad](../install/) already.</Alert>

Think of a workflow a shared blueprint for every agent that does the same kind of work. Workflows control where agents start, which CLI they run, and what flags their agents are launched with such as the `--dangerously-skip-permissions` flag for Claude.

You can have multiple workflows per directory, such as a bugfix workflow, and a feature workflow, that apply different settings to their implementer agents.

Each workflow also has one orchestrator agent, responssible for managing every implementer agent within it.

## Creating your first Workflow

Let's clone a real repository to work in. This guide uses Neovim:

```sh
git clone https://github.com/neovim/neovim ~/neovim
cd ~/neovim
```

Next, run `komrad open` and press `w` in the panel, name the workflow `neovim` and submit it with `<C-s>` to create it. By default, your workflow takes the current directory as it's active directory:

The orchestrator writes no code of its own. You tell it what you want done, and it spawns agents into the workflow to do the work, passes messages between them, and gathers what they find. The coordinator is the "brains" of every subagent that is doing real work and often stitches their work together or passes work between them.

You can learn more about the orchestrator and the other kinds of agent in the [agents](../agents/) guide.

## Shared context

Workflows can hold _shared context_ for each implementer agent. This is where you put what you would otherwise tell each agent by hand: how tests run, how branches are named, and so forth.

In our Neovim example, that might be: "Run make lint before committing any Lua change."

It comes after komrad's own briefing and your [global context](../../config/#context).

## Worktrees

Like most agent orchestrators, komrad ships with first-class support for [worktrees](https://git-scm.com/docs/git-worktree).

Komrad can automatically create a worktree for each agent, which is cut fresh from a base branch. The agent works on a branch of its own, and the worktree is removed when the agent is deleted.

The workflow's directory has to be an ordinary clone for this to work.

Worktrees go in [`worktrees.dir`](../../config/#worktrees.dir) unless the workflow names its own location. Each worktree is a clean checkout, so a workflow can list files to copy in, like local environment files, or local packages. For anything heavier, like installing or networking configuration, use a [hook](../hooks/) instead.

<Alert variant="info">
  Agents do not have to create worktrees, but be careful: those that do not will run directly inside of the directory
  specified.
</Alert>

The worktree's branch is worked out from your repository's clone when you create the workflow. New worktrees are cut from it and an agent's work is measured against it. If the clone loses that branch, `komrad doctor` says so.

## Archiving and restoring

Archiving a workflow puts it into cold storage: you can hard-delete it later, but for now, it'll be hidden from your workflow view.

Nothing is destroyed, and search still finds what the agents said. However, the agents inside of the workflow will be shut down. Restoring brings the whole workflow back, along with its agents in a stopped state, and ready to resume.
