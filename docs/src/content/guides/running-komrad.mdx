Komrad splits into a panel and an engine. The panel is the terminal UI you work in. The engine is the komrad server and everything it manages: the agents running in tmux, their worktrees on disk, and the Postgres database that holds every record. When you install komrad on a laptop, both halves run there and only you can reach them. [Installing komrad](../install/) covers that setup.

A remote engine runs on a machine that stays on. Agents keep working after you close your laptop, and other people can point their own panels at the same engine. This guide describes the parts a remote engine needs without assuming a cloud provider. [Komrad's engine](../komrads-engine/) describes how komrad runs its own on AWS.

Before the panel talks to an engine, it gets a token from your identity provider. It sends each request with that token over HTTPS to a proxy on the engine host. The proxy holds the TLS certificate and passes the request to the komrad server on a loopback port, and the server checks the token before it handles the request.

Agents run on the same host, inside a tmux server that komrad starts and owns. Each agent works in its own git worktree and uses komrad's MCP tools to talk to the server, which is how it sends mail and asks for reviews. When an agent pushes a branch, git talks to the forge directly. The server talks to the forge too, to keep track of each task's pull request.

## State

A remote engine keeps its state in two places. Postgres has every record komrad writes. A disk has the worktrees, the agent CLIs' logins and komrad's config file. If you put the database on its own server and the disk on a separate volume, you can throw the host away and build a new one, and you lose only the processes that were running on it. Once the new host is up, you resume the agents that stopped.

However, restarting komrad is even easier than that. Since the agents belong to komrad's tmux server, which keeps running even after komrad's server restarts, you can reboot the server at any time without losing any agents or state.

## Access to a remote engine

Every request to a remote engine has to say who sent it. Komrad keeps no passwords. People sign in through an OpenID Connect provider, Google or Okta for example, and the engine checks the token from that sign-in against the access grants its owner has given out. A grant gives full access. Anyone who holds one can do anything on the engine, including open a shell on the host as the account the agents run as. [Access](../engine-access/) covers sign-in and grants in detail.

The komrad server listens only on loopback, and the proxy in front of it is the only thing exposed to the network. Komrad's engine uses Caddy because it gets and renews its own certificate, but any proxy that speaks HTTP/2 will work.

An engine can also sit on a private network instead of the internet. Komrad's engine sits on a Tailscale tailnet, and Tailscale issues Caddy's certificate. Other private networks, Headscale included, need your own domain with a DNS challenge or a certificate authority every laptop trusts. Agents run unreviewed code, so stop the engine from opening connections into the network.

Operators need a shell on the host for upgrades and debugging. Give them one that doesn't need an open port on the internet. On AWS, komrad's engine uses Systems Manager sessions for this.

## Forge credentials

Agents push branches and the server reads pull requests, so the engine needs credentials for each forge it works with. On a laptop your personal token is fine. On a shared engine, every agent's push would show up as you, and the token would sit on the engine's disk for as long as it lasts, which for a personal token can be months. Give a shared engine credentials of its own that expire within a day. [Forge credentials](../forge-credentials/) explains how to set that up for GitHub and GitLab.

## Checklist

Before you stand up an engine, have each of these ready or know where it will come from:

- A Linux host that stays on.
- A volume for the worktrees and logins that will outlive the host.
- A Postgres database the host can reach.
- A name and certificate for the engine, from a domain or a private network, and a proxy to terminate HTTPS.
- An OpenID Connect provider with komrad registered on it.
- Forge credentials that belong to the engine.
- A way for operators to get a shell without opening a port to the internet.

[Standing up an engine](../standing-up-an-engine/) builds all of this on AWS.
